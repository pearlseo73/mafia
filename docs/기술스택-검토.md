## 1. 결론: 확정 스택으로 전부 구현 가능

| 영역 | 기술 | 가능 여부 |
|---|---|---|
| STT | Web Speech API (브라우저) | ✅ 가능 — 단 제약 있음(§2-2) |
| 얼굴/표정 분석 | face-api.js (`@vladmandic/face-api`) | ✅ 가능 |
| LLM 로그 분석 | GPT 모델 + **Spring AI** | ✅ 가능 — 단 GMS 호환성 확인 필요(§4-1) |
| Python 서버 | **사용하지 않음** | ✅ 불필요 |

Python을 두지 않는 것이 이 팀 구조에 더 맞다. 얼굴 분석은 명세 19-3이 이미 클라이언트 처리를 요구하고, LLM 호출은 HTTP 요청이라 Spring에서 직접 하는 편이 네트워크 홉이 하나 줄어든다.

## 2. 유의사항 3건

### 2-1. face-api.js와 MediaPipe는 병행이 아니라 교체 관계

**둘을 동시에 로드하지 않는다.** tfjs(WebGL 컨텍스트)와 MediaPipe WASM이 함께 GPU·메모리를 점유하고, 그 옆에서 LiveKit이 6명의 비디오를 디코딩한다. 저사양 기기에서 프레임 드랍이 먼저 온다.

| | face-api.js | MediaPipe Face Landmarker |
|---|---|---|
| 출력 | 감정 7개 클래스 | blendshape 52개 |
| 동요 지수 적용 | **즉시 가능** | 감정 매핑을 직접 설계해야 함 |
| 랜드마크 정밀도 | 낮음 | 높음 |

**방침: face-api.js로 시작 → 표정 표현력이 부족하면 MediaPipe로 교체.**
MediaPipe가 필요해지는 시점은 rPPG(심박 추정)를 할 때다. 이마·뺨 ROI를 정확히 잡으려면 정밀 랜드마크가 필요하다. 현재 우선순위 낮음(보류).

### 2-2. Web Speech API가 실패해도 Python은 필요 없다

"Python 없이 간다"는 방침은 STT 리스크에 묶여 있지 않다.

| 순서 | 방식 | Python | 비고 |
|---|---|---|---|
| 1안 | Web Speech API (브라우저) | 불필요 | 무료·저지연. **리스크: LiveKit과 마이크 경쟁** |
| 2안 | 오디오 청크 → Spring → **Whisper API (HTTP)** | 불필요 | 지연·비용 증가, 스택 구조 유지 |
| ✗ | 브라우저 Whisper WASM | 불필요 | 6명 + WebRTC와 CPU 경쟁 → 권하지 않음 |
| ✗ | Python + faster-whisper | 필요 | 방침 위반 |

### 2-3. GPT 사용 시 Structured Output은 선택이 아니라 필수

칭호 배정(전원 JSON 배열), AI 심판 결과(사유 + 대상 ID) 같은 산출물은 프롬프트로 "JSON으로 답해줘"라고 부탁하는 것만으로는 파싱이 계속 깨진다. **스키마를 강제**해야 한다.

Spring AI에서는 `ChatClient`의 `.entity(Class)` 로 처리한다(내부적으로 `BeanOutputConverter`). AI 심판은 스트리밍이 필요하므로(명세 20-5: 사유 먼저 → 대상 나중) 스트리밍과 스키마를 함께 쓰는 형태가 된다.

## 3. 파트별 코드 작업 범위

### 3-1. 기능별 Vue / Spring 분담

| 기능 | Vue 코드 | Spring 코드 |
|---|---|---|
| 얼굴/표정 분석 | **전부** (추론·산식·전송) | 점수 중계·브로드캐스트만 |
| 조간신문 | 결과 표시 | **전부** (로그 조회·프롬프트·LLM·검증) |
| AI 심판 | 결과 표시(스트리밍 수신) | **전부** |
| 진술대조권 / 키워드 뽑기 | 아이템 UI·결과 표시 | **전부** |
| 칭호 부여 | 결산 화면 표시 | **전부** (지표 집계 + LLM) |
| **STT 수집** | **전부** (인식·전송) | 로그 저장(Redis) |

### 3-2. "로그 분석은 Vue와 Spring 둘 다 작성하는가"

**분석 로직은 100% Spring이다.** Vue 쪽은 분석 코드가 아니라 **입력(STT 수집)과 출력(결과 표시)** 이다.

```
[Vue] Web Speech API 인식 ──► [Spring] Redis 로그 저장
                                  │
                              Spring AI ──► GPT
                                  │
[Vue] 결과 표시 ◄──── WebSocket ───┘
```

### 3-3. AI 담당자가 직접 작성할 것 / 프론트에 넘길 것

| 구분 | 내용 |
|---|---|
| **AI 담당 (Vue)** | `useSpeechLog.ts` — STT 수집·전송<br>`useFaceAgitation.ts` — 얼굴 분석·동요 지수 |
| **AI 담당 (Spring)** | 로그 저장·조회, 프롬프트, Spring AI 호출, 결과 검증, 지표 집계 |
| **프론트 담당** | 위 composable을 화면에 붙이는 작업, 신문 모달·심판 화면·결산 화면·아이템 UI |

**STT 수집을 AI 담당이 직접 작성해야 하는 이유:** 발화를 어떤 단위로 자르고 어떤 시각을 붙여 보낼지가 로그 품질을 결정하고, 그 품질이 LLM 기능 5종의 결과를 좌우한다. 프론트 담당자에게는 이 판단의 근거가 없다.

**composable로 납품하고 화면 조립은 프론트가 맡는 경계**를 지키면 서로의 작업이 막히지 않는다.

## 4. 실험 레포의 Spring 프로젝트 구성

이 레포 하위에 Spring 프로젝트를 만들어 **AI 부분만** 구현한다. Colab 검증은 종료.

### 4-1. 먼저 확인해야 할 것 — GMS의 OpenAI 호환성

**Spring AI를 쓸 수 있는지가 여기에 달려 있다.**

| GMS가 OpenAI 호환 엔드포인트인가 | 방법 |
|---|---|
| 예 | Spring AI OpenAI 스타터의 `base-url`을 GMS로 지정 → 그대로 사용 |
| 아니오 | Spring AI 사용 불가 → `WebClient`로 직접 호출 (구조는 유지, `.entity()`·`.stream()` 편의는 직접 구현) |

버전 주의: Spring AI는 1.0 GA 시점에 스타터 아티팩트 ID가 변경되었다(`spring-ai-openai-spring-boot-starter` → `spring-ai-starter-model-openai`). 참고 자료를 볼 때 버전을 먼저 확인할 것.

### 4-2. 팀 레포로 이식 가능하게 설계

게임 로직(방·세션·투표 상태)이 없는 상태에서 AI만 구현하므로, **외부 의존을 인터페이스로 끊어두면** 팀 레포로 그대로 옮길 수 있다.

```
UtteranceRepository (interface)
 ├─ FakeUtteranceRepository   ← 실험 레포: 샘플 로그 픽스처
 └─ RedisUtteranceRepository  ← 팀 레포: 실제 구현

GameSnapshotProvider (interface)   ← 생존자·역할·투표 내역·아이템 사용 이력
 ├─ FakeGameSnapshotProvider
 └─ (팀 레포 구현)
```

- 프롬프트는 **리소스 파일로 분리**(`resources/prompts/*.st`)해 버전 관리한다. 코드에 문자열로 박으면 프롬프트 수정마다 재빌드가 필요하다.
- 각 AI 기능을 **REST 엔드포인트로 노출**하고 `.http` 파일이나 curl로 반복 호출하면 Colab을 대체하는 프롬프트 검증 루프가 된다.
- **샘플 발화 로그 픽스처**를 만들어 둔다(정상 대화 / 침묵 플레이어 / 모순 있는 발언 / 발화 극소량). §7-5의 환각 방어를 검증할 때 필요하다.

### 4-3. 예상 패키지 구조

```
ai/
 ├─ newspaper/     조간신문      (Task 17)
 ├─ judgment/      AI 심판       (Task 20)
 ├─ item/          진술대조·키워드 (Task 16)
 ├─ title/         칭호 부여      (Task 22 신규)
 ├─ log/           발화 로그 저장·조회 + 가시성 격리
 └─ common/        프롬프트 로딩, LLM 클라이언트 설정, 폴백·타임아웃
```

`log/` 패키지에서 **공개 로그와 마피아 로그의 조회 경로를 분리**하는 것이 중요하다([AI기능-구현설계.md §2-2](AI기능-구현설계.md)).
