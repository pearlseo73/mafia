## 0. 입력을 만드는 규칙 (프롬프트보다 이게 먼저다)

| 항목 | 값 | 근거 |
|---|---|---|
| 로그 소스 | `utt:{roomId}:public` **만** | 밤 로그가 섞이면 마피아 신원 노출 |
| 라운드 범위 | **전체 라운드** | 라운드 간 말이 바뀌는 것이 이 아이템의 핵심 ([§7-1](../../docs/AI기능-구현설계.md)) |
| 화자 범위 | **지목 대상 1명의 발화만** | 아래 참조 |
| 시간 범위 | **아이템 사용 시각까지** | 그 이후 발화는 사용 시점에 존재하지 않았다 |
| 역할 정보 | **넣지 않는다** | 마피아/시민을 알면 판정이 오염된다 |

**대상 1명의 발화만 주는 이유:** 전체 대화를 주면 LLM이 다른 사람의 발언을 대상의 발언으로 인용하는 실수가 생긴다. 애초에 대상의 발화만 넣으면 그 오류가 **구조적으로 불가능**해진다. [§2-2](../../docs/AI기능-구현설계.md)의 "가져오는 키가 애초에 다르다"와 같은 접근이다.

> **미결 1.** 이렇게 하면 대화 맥락이 사라져서 **"회피"** 탐지가 약해진다. "본인 생각은 뭐예요"(정민재 21:01:05)에 박도현이 답을 피했다는 판정은 질문이 있어야 가능하다. §7-1은 목적을 "모순·**회피**"로 적고 있으므로, 회피까지 볼 거라면 대상 발화 직전 1~2줄을 맥락으로 덧붙이는 형태를 검토해야 한다. **v0에서는 모순만 본다.**

> **미결 2.** 투표 내역을 대조할지 (체크리스트 TC-3). "강예린에게 넣겠다"(21:01:12) ↔ 실제 `박도현→최지우` 불일치는 발화 로그만으로는 검출 불가능하다. **v0에서는 넣지 않는다.**

### 발화 임계값 — LLM을 호출하지 않는 조건

[§7-5](../../docs/AI기능-구현설계.md)에 따라 서버가 먼저 걸러낸다.

```
대상의 발화가 3건 미만  또는  총 글자수 40자 미만  →  LLM 호출 없이 즉시 응답
```

응답은 `hasFindings: false` + `noFindingReason: "INSUFFICIENT"`. 최지우(2건·25자)가 여기서 걸린다.

## 1. 출력 계약 (LLM이 반환하는 JSON)

**LLM은 발화 원문을 쓰지 않는다. 발화 번호만 반환하고 서버가 원문으로 치환한다.**

이게 인용 환각을 막는 가장 확실한 방법이다. 원문을 생성하지 않으면 없는 발언을 만들어낼 수 없다.

```jsonc
{
  "hasFindings": true,
  "summary": "한 문장. 무엇과 무엇이 충돌하는지만.",
  "contradictions": [
    {
      "utteranceIds": ["u2", "u6", "u9"],   // 서로 충돌하는 발화 2개 이상
      "reason": "왜 충돌하는지 한 문장"
    }
  ]
}
```

모순이 없을 때:

```jsonc
{ "hasFindings": false, "noFindingReason": "NO_CONTRADICTION", "contradictions": [] }
```

`noFindingReason`: `NO_CONTRADICTION` | `INSUFFICIENT`
→ 화면에 나갈 한국어 문장("모순이 발견되지 않았습니다" / "분석할 발언이 부족합니다")은 **서버가 이 enum으로 고른다.** LLM 문구를 그대로 쓰면 매번 표현이 달라진다.

**서버가 감싸서 내보내는 부분** (LLM은 모른다) — `requestId`, `itemCode`, `targetPlayerId`, 그리고 `utteranceIds` → `{round, time, text}` 치환.

> 이 때문에 [AI-API명세 §2-5](../../docs/AI-API명세.md)의 `contradictions[].quote`는 **LLM 출력이 아니라 서버 조립 결과**가 된다. 명세 주석 보강 필요.

## 2. 프롬프트

### System

```
당신은 마피아 게임의 발언 기록을 검토하는 분석관이다.
한 플레이어의 발언 목록을 받아서, 서로 앞뒤가 맞지 않는 발언을 찾아낸다.

규칙:
1. 주어진 발언 목록 밖의 내용은 절대 사용하지 않는다. 추측하거나 보충하지 않는다.
2. 발언 원문을 다시 쓰지 않는다. 발언 번호(u1, u2 ...)로만 지목한다.
3. 모순이 없으면 없다고 답한다. 이것은 실패가 아니라 정상적인 결과다.
   억지로 모순을 만들어내는 것이 이 작업에서 가장 나쁜 실패다.
4. 판단 기준은 "같은 대상에 대한 태도·사실 주장이 서로 양립할 수 없는가"다.
   생각이 바뀔 수 있는 의견 변화와, 과거를 다르게 진술하는 것은 다르다.
   후자만 모순으로 본다.
5. 누가 마피아인지 추측하지 않는다. 발언 간의 일관성만 본다.
6. 결과는 지정된 JSON 형식으로만 답한다.
```

**규칙 4가 이 프롬프트의 핵심이다.** "생각이 바뀌었다"(마음이 바뀜)와 "과거를 다르게 말한다"(처음부터 믿었다 / 의심한 적 없다)를 구분하지 못하면, 정상적인 의견 변경까지 모순으로 잡아낸다.

### User

```
분석 대상: {targetName}

발언 목록 (시간순):
{utterances}
```

`{utterances}` 렌더링 형식 — 라운드는 반드시 표시한다. 라운드 간 변화가 판정의 근거다.

```
u1 [R1] 이하윤 씨 말도 일리가 있어요 보통 마피아가 먼저 판을 짜려고 하니까
u2 [R1] 저는 강예린 씨가 제일 수상해요 아까부터 논의를 계속 막고 있어요 이번 투표는 강예린 씨한테 넣을 생각입니다
...
```

시각(`21:01:12`)은 넣지 않는다. 라운드만 있으면 충분하고, 초 단위 시각은 토큰만 쓴다. 서버가 `u2` → 시각을 되돌릴 수 있으므로 화면 표시에는 문제없다.

## 3. Spring AI로 옮길 때 주의

- Spring AI `PromptTemplate`의 기본 델리미터가 `{}`다. **위 JSON 예시를 `.st` 파일에 그대로 넣으면 중괄호가 변수로 해석돼서 깨진다.** 출력 형식 지시는 `BeanOutputConverter`에 맡기고 프롬프트 본문에서 빼거나, 델리미터를 바꿔야 한다.
- `BeanOutputConverter`는 자체 형식 지시문을 프롬프트 뒤에 덧붙인다. 위 System 규칙 6번과 중복되면 지워도 된다.
- temperature는 **낮게**(0~0.2). 창작이 아니라 판정이다.
