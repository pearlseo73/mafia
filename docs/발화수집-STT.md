# 발화 수집 — 브라우저 STT → Redis

> 최종 수정: 2026-07-28
> 실측: [log_analysis/stt-test/index.html](../log_analysis/stt-test/index.html) 로 직접 녹음
> 변형 픽스처: [발화로그-STT변형-설명.md](../log_analysis/scenario/scenario1/발화로그-STT변형-설명.md)

AI 기능의 **입력이 어디서 어떤 모양으로 오는지**를 정한 문서다. 프롬프트를 아무리 다듬어도 입력이 깨져 있으면 결과가 깨지므로, 프롬프트 설계보다 이것이 먼저다.

---

## 1. STT 는 브라우저에서 한다 (확정)

WebRTC 화상까지 서버에서 처리하면 부담이 크고, 파이썬 서버를 따로 띄우지 않기로 했다. Chrome 의 Web Speech API(`SpeechRecognition`)를 쓴다.

### 따라오는 것들

| | 내용 |
|---|---|
| **화자 구분이 공짜다** | 각자 자기 브라우저에서 자기 마이크만 인식한다. 오디오 하나에서 목소리를 갈라내는 문제가 아예 없다 |
| **Chrome / Edge 만 된다** | Firefox 미지원. 팀에서 Chrome 고정으로 간다 |
| **localhost 또는 https 필수** | `file://` 로 열면 마이크가 열리지 않는다 |
| **인터넷이 필요하다** | Chrome 은 오디오를 구글 서버로 보내 인식한다. 온디바이스가 아니다 — 개인정보 항목으로 한 번 짚어야 한다 |
| **클라이언트가 조작할 수 있다** | 말하지 않은 문장을 서버로 보낼 수 있다. 프로젝트 수준에서는 넘어가지만 알고는 있어야 한다 |

### 에코가 진술대조권에 치명적이다

스피커로 나오는 남의 목소리가 내 마이크에 들어가면 **그 말이 내 발화로 저장된다.** 하지 않은 말로 모순 판정을 받는 것이다. 헤드셋 권장 + `echoCancellation` 으로 줄이되 완전히 막히지는 않는다.

## 2. 저장 구조 — 키 2개에 시간순으로 쌓는다

```
utt:{roomId}:public    낮 계열 전부
utt:{roomId}:night     밤 마피아 대화만
```

발화 한 건의 모양. `phase` 가 이번에 새로 생긴 필드다.

```jsonc
{ "t": "21:06:20", "speaker": "초코비", "round": 2,
  "phase": "DAY_DISCUSSION", "text": "마음이 바뀐 겁니다 ..." }
```

### 사람별·라운드별로 쪼개지 않는 이유

6명 × 3라운드 × 4페이즈면 키가 72개가 되고 라운드 수는 미정이라 가변이다. 그러면 **조간신문·AI 심판이 전체 대화를 복원할 때 72개를 꺼내 시각으로 정렬해 병합해야 한다.** 그 코드가 틀리면 대화 순서가 어긋난 로그로 AI 가 판단한다. TTL 도 72개에 각각 걸어야 한다.

하나로 쌓으면 **꺼낸 뒤 걸러내기만** 하면 된다. 합치는 것보다 걸러내는 게 쉽다.

| 기능 | 필터 조건 |
|---|---|
| 진술대조권 | `speaker == 대상` · 전체 라운드 · `t < 사용시각` |
| 키워드 뽑기 | 같음 (2026-07-28 명세 변경 전에는 현재 라운드만) |
| 조간신문 | 전원 · 지난 라운드 |
| AI 심판 | 전원 · 이번 라운드 토론 |
| 칭호 부여 | 전원 · 게임 전체 (+ 밤 로그 opt-in) |

6명이 3분씩 3라운드 말해도 수백 건, 수십 KB다. 필터가 부담될 규모가 아니라 성능 때문에 쪼갤 이유가 없다.

**사람별 표 형태는 화면에 보여줄 때 쓴다.** 저장 구조와 표시 구조를 같게 맞출 필요가 없다.

### 밤 로그는 반드시 다른 키에

같은 목록에 넣고 "낮 것만 골라 쓰기" 로 하면, 어느 기능에서 한 번만 필터를 빠뜨려도 마피아 신원이 노출된다. 키를 처음부터 갈라두면 실수해도 새지 않는다.

### 원문은 Redis + TTL 만

음성에서 나온 텍스트는 개인정보이고 게임이 끝나면 필요가 없다. MySQL 에 넣으면 지우는 코드를 따로 만들어야 하고 안 지우면 계속 쌓인다. MySQL 에는 승패·통계만 남긴다.

## 3. `round` · `phase` 는 서버가 붙인다

브라우저는 **텍스트만** 보낸다. 나머지는 서버가 채운다.

- **누가** — WebSocket 연결에 이미 붙어 있다
- **round · phase** — 서버가 타이머를 재면서 갖고 있는 값이다
- **시각** — 서버가 받은 시점에 찍는다
- **어느 키에 넣을지** — 지금 밤이면 night, 아니면 public

그래서 클라이언트가 조작할 수 있는 건 텍스트뿐이다.

`phase` 가 필요한 이유는 발언의 뜻이 시점에 따라 달라지기 때문이다. "저는 딸기우유 씨입니다" 는 `DAY_VOTE` 에서는 투표 선언인데, 페이즈 정보가 없으면 자기소개로 읽힌다. **실제로 이 오독으로 없는 모순이 만들어진 적이 있다** (2026-07-28 실측).

**2026-07-29 에 수치로 확인했다.** 모순이 없는 인물(라면왕)을 지목했을 때 페이즈 없이 3회 중 3회 오독했고, 페이즈를 넣으면 3회 중 0회로 사라졌다. 모순이 있는 인물(초코비)은 두 조건 모두 정확해서 **되던 케이스가 망가지지도 않았다** → [진술대조 §2-3 실측 2](../log_analysis/prompts/진술대조.md)

이 문장이 원본 픽스처에도 있으니 **STT 탓이 아니다.** 같은 라운드에 명시형("정민재 씨에게 투표하겠습니다")과 생략형("저는 강예린 씨입니다")이 섞여 있고, 주어 생략이 흔한 한국어에서 자연스러운 변이다. 문장만으로는 두 해석을 가릴 수 없다.

→ `phase` 는 "있으면 좋은 것"이 아니라 **없으면 진술대조권이 깨지는 것**이다. 팀 요청 항목으로 [AI-API명세 §5-3](AI-API명세.md) 에 올려뒀다.

### 경계 타이밍 — 밤↔낮만 조심하면 된다

STT 는 말이 끝난 뒤에 결과를 준다. 그래서 전환 직전에 시작한 발화가 직후에 도착하면 페이즈가 하나 밀린다. 낮 안에서는 몇 초 차이라 문제가 안 되지만, **밤 발화가 낮 키에 들어가면 마피아가 노출된다.** 밤↔낮 경계에는 여유를 둔다.

## 4. 실측 — 무엇이 어떻게 깨지는가 (2026-07-28)

[발화로그-공개.txt](../log_analysis/scenario/scenario1/발화로그-공개.txt) 의 박도현 발화 9건을 사람이 직접 읽어서 받았다. 노트북 마이크, 혼자서 또박또박. **실제 게임에서는 6명이 겹쳐 말하므로 이보다 나쁘다.**

### 4-1. 쪼개지지 않는다. 합쳐진다

걱정했던 "한 발언이 여러 조각" 이 아니라 반대였다. 대본 9건이 **8건**으로 왔고, 두 발언이 한 건으로 합쳐졌다. 3초를 쉬어도 끊기지 않았다.

합쳐지면 **한 발화 안에 서로 다른 취지의 말이 섞인다.** 진술대조권에서 이게 직접 문제가 된다 → §5.

### 4-2. 이름이 가장 심하게 흔들린다

```
이하윤 → 이하연
강예린 → 강혜린 / 강예은     (한 줄 안에서도 갈린다)
```

STT 는 사전에 없는 사람 이름을 못 맞춘다. 헤드셋으로도 나아지지 않는다.

### 4-3. 뜻이 사라지거나 뒤집힌다

| 원본 | 인식 결과 | 사라진 것 |
|---|---|---|
| 방어권 있습니다 | **방학과** 있습니다 | 방어권 주장 |
| 넣을 생각입니다 | **너를** 생각입니다 | 투표 의사 |
| 찬성했습니다 | **편성**했습니다 | 자기모순의 근거 |
| 다들 시민이라고 | 근데 **신**이라고 | 시민 주장 |
| 삼분 동안 | **3년** 동안 | — |
| 시간 낭비 | 시간 **남비** | 키워드 대상 표현 |

`편성했습니다` 가 특히 고약하다. **정상적인 한국어라서 사전 교정으로 잡을 근거가 없다.**

### 4-4. 짧은 발언이 취약하다

`네` → `그때`, `다들 넣었나요` → `다 들었나요`, `이제 셋이네요` → `이제 세 시네요`.

### 4-5. `confidence` 는 쓸모가 없다

**틀린 것은 자신 있게 오고, 맞은 것이 낮게 온다.** 0.8 미만으로 표시된 것은 `그때`(짧은 대꾸)와 `글쎄요`(정확히 맞은 것) 둘뿐이었고, 위 4-3 의 위험한 오인식은 **전부 0.8 이상**이었다.

→ **서버가 "이 발화는 못 믿겠다" 고 판단할 방법이 없다.** 오인식된 문장이 깨끗한 문장과 구별 없이 Redis 에 들어가고 그대로 AI 에게 간다.

### 4-6. 숫자는 알아서 정규화된다

"일라운드" 라고 말해도 `1라운드` 로 적힌다. 이건 도움이 되는 쪽이다.

## 5. AI 기능에 주는 영향

| 기능 | 영향 |
|---|---|
| 🔍 진술대조권 | 모순의 근거 단어가 사라지면 **입력에 그 사실이 없다.** 프롬프트로 못 고친다. 반대로 뜻이 뒤틀려 없는 모순이 만들어질 수도 있다 |
| 🏷️ 키워드 뽑기 | 부분 문자열 검사가 무력해진다 — `시간 남비` 가 원문이니 통과한다. **유저는 상대가 하지 않은 말을 키워드로 본다** |
| 📰 조간신문 · 🏆 칭호 | 창작이라 상대적으로 내구성이 있다. 인용의 정확성이 요구되지 않는다 |

### 발화 병합이 만드는 새 문제

변형 픽스처의 `21:06:20` 이 이렇게 됐다.

```
원본  21:06:15  마음이 바뀐 겁니다 그게 이상한가요          ← 모순으로 잡으면 안 되는 것
      21:06:20  저는 처음부터 강예린 씨를 믿었습니다        ← 반드시 잡아야 하는 것
변형  21:06:20  (둘이 한 발화)
```

발화 번호가 하나뿐이니 **잡으면 정답과 오답이 동시에 성립한다.** 화면 인용문에도 해명과 모순이 한 덩어리로 나간다. **프롬프트로 풀 문제가 아니라 발화 경계 문제다.**

## 6. 이름 흔들림 대응 — 결정 대기

화자는 서버가 확실히 안다. 흔들리는 것은 **발화 안에서 남을 지칭한 이름**뿐이다. 그래서 문제 범위는 절반이다.

| 방법 | 평가 |
|---|---|
| **닉네임을 번호로** — 화면에 번호 배지, 호칭도 번호 | 숫자는 STT 가 거의 안 틀린다. 오프라인 마피아 게임의 관습이라 어색하지 않다. 다만 강제할 수 없다 |
| **프롬프트에 방 참가자 명단을 준다** | 서버가 이미 아는 정보라 비용이 0 이다. LLM 이 발음 유사도를 사람처럼 판단해 `강혜린`→`강예린` 을 맞출 가능성이 높다. **과하게 동일시할 위험은 있다** |
| ~~서버가 편집거리로 교정~~ | 닉네임이 `xXkiller`·`ㅋㅋㅋ` 처럼 한국어 발음과 대조 불가능한 형태일 수 있다. 사람들은 닉네임을 줄여 부르기도 한다 |

**둘은 배타적이지 않다.** 번호 호칭으로 발생을 줄이고 명단으로 남은 것을 흡수하는 조합이 자연스럽다. 명단 주입은 [진술대조 프롬프트](../log_analysis/prompts/진술대조.md) 에서 실제로 시도했다.

**게임 핵심 동사는 사전 교정 대상으로 삼을 값어치가 있다** — 찬성·반대·의심·믿다·투표·처형·방어권. 이름보다 우선순위가 높을 수 있다. `편성했습니다` 처럼 멀쩡한 단어로 바뀐 경우는 여전히 못 잡는다.

## 7. 아직 안 해본 것

- **헤드셋으로 재측정** — 게임 용어 오인식이 얼마나 줄어드는지. 많이 나아지면 사전 교정 부담이 준다
- **여러 명 동시 발화** — 에코와 겹쳐 말하기. 실제 게임 조건이다
- **발화 유실** — Chrome 은 조용하면 인식을 끊는다. 3분 토론 중 몇 번 재시작되는지, 그 사이 발화가 사라지는지. 측정 페이지에 재시작 카운터가 있다
- **조각 병합을 서버에서 할지** — 같은 화자가 몇 초 안에 연달아 말한 걸 합칠 기준. §5 의 문제와 반대 방향이라 신중해야 한다
