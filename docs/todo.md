### 앞선 세 기능과 다른 점

1. **역할을 LLM에 준다.** 게임 종료 = 역할 공개 시점이라 절대 규칙 2의 유일한 예외다. 밤 로그도 opt-in(TC-27)

### 정해야 할 것 — 첫째가 나머지를 좌우한다

| | 안 | 평가 |
|---|---|---|

## 진술대조권 — 확정된 것과 미결

전체 근거는 [프롬프트 §2-3](../log_analysis/prompts/진술대조.md)에 있다. 여기는 요약이다.

### 확정

- **LLM이 짝을 직접 고른다. 단 하나만.** 여러 개를 요구하면 회차마다 개수와 내용이 흔들렸다
- **프롬프트 규칙은 3개** — 원문 재작성 금지 · 마피아 추측 금지 · JSON only. 나머지는 모델이 안 배워도 하거나, 넣어도 안 지켜졌다
- **USER 마지막 줄은 조건형이어야 한다** — `모순이 있는 경우에만`. 명령형이면 없어도 만들어낸다
- **입력은 대상 발화만.** 라운드 · **페이즈** · 시각을 붙이고 화자는 뺀다 (`u12 [R2 투표 21:08:10]`)
- **컷오프는 코드가 한다.** `t < now`이고 `now` 자체도 제외
- **`phase`가 없으면 TC-5가 깨진다.** Redis 저장 시 붙여달라고 요청할 항목
- **번호 검증은 코드가.** `by_id` 밖의 번호 제거, 2개 미만이면 `hasFindings=false`
- **`reason`은 LLM이 쓴다.** 서버 조립은 판정 B안 전제였으므로 지금은 해당 없음

### 미결

- **어느 짝이 나올지 회차마다 다르다.** 셋 다 정답이지만 재현되지 않는다. 같은 대상을 두 번 대조하면 다른 답이 나온다. `u7`×`u8`(25초 간격 정면 자기모순)이 `u2`×`u5`("마음이 바뀐 겁니다"라는 해명이 붙어 반박 가능)보다 강하므로, **고르고 싶으면 판정 B안이 필요하다**
- **`u5`×`u6`을 못 잡는다** — "처음부터 믿었습니다" 하고 2분 뒤에 그에게 투표. 유효한 후보인데 짝을 하나만 받아서 안 나온다. 여러 개를 요구했을 때 흔들리는지 **정제된 입력에서 다시 재봐야 한다**
- **생존 검사(TC-7) 미구현.** 소금빵은 R1 밤 사망자라 실서비스에서는 `TARGET_NOT_ALIVE`로 먼저 막혀야 한다. 지금은 임계값까지 흘러가 우연히 같은 결과가 나온다
- **투표 내역(TC-3) 미구현.** `phase`와 같은 "서버가 아는 사실"이라 함께 검토할 가치가 있다
- **`21:06:20` 병합 문제** — 해명("마음이 바뀐 겁니다")과 모순("처음부터 믿었습니다")이 한 발화다. 프롬프트로 풀 문제가 아니다 → [발화수집-STT §5](발화수집-STT.md)
- **임계값 `3`·`40`은 잠정값.** R1 토론 중에 쓰면 6명 중 3명이 미달이다 ([T8](결정필요사항.md))

## 키워드 뽑기 — 명세가 바뀌었다

오늘 노트북에서 다시 설계했다. 기존 [프롬프트 문서](../log_analysis/prompts/키워드뽑기.md)와 `ai-lab` 구현이 이 변경을 아직 반영하지 않았다.

| | 기존 | **오늘 확정** |
|---|---|---|
| 로그 범위 | 현재 라운드만 | **전체 라운드** (처음부터 사용 시점까지) |
| 개수 | 3~5개 | **정확히 5개** |
| 묶기 | 없음 | **의미로 묶는다.** 글자가 달라도 같은 태도면 하나로 |
| 어미 | 원문 그대로 | **사전형으로 다듬는다** (`억울하면` → `억울하다`) |
| 금지 | 상위 개념어 | **요약 라벨 금지** (`소극적 태도`, `근거 없는 주장`) |
| 근거 | 없음 | `evidence`로 발화 번호를 받는다 |

**로그 범위를 전체로 넓히면 진술대조권과 입력이 같아진다.** 산출물(키워드 vs 모순)로만 구분되는 셈이다. [§7-1](AI기능-구현설계.md)의 차별화 근거를 다시 볼 필요가 있다.

### 🔴 알려진 결함 (2026-07-29 발견, 미수정)

딸기우유 11건(`now` = 21:07:30) 결과를 원문과 대조했다.

```
시간 낭비     count=3  ['u1', 'u3', 'u2']    ← 묶기 정확
근거 없다     count=2  ['u6', 'u3']          ← u3 재사용, 오배정
숨길 게 없다   count=1  ['u5']
억울하다      count=1  ['u4']
비효율적이다   count=1  ['u3']                 ← u3 세 번째, 시간 낭비와 같은 묶음
```

- **`u3` 하나가 세 키워드에 배정됐다.** `u3`("방식이 비효율적이라고 한 거잖아요")에는 근거 얘기가 없는데 `근거 없다`의 evidence로 들어갔다. 실제 근거는 `u6` 하나뿐인데 `count=2`다
- **`비효율적이다`는 `시간 낭비`와 같은 묶음이어야 한다.** 프롬프트가 예시로 명시한 묶음인데 분리됐다
- 원인은 **5개 강제**로 보인다. 태도가 드러나는 발화가 5개가 안 되는데 5개를 요구하니 이미 쓴 발화를 재사용한다
- **R2 발화 3건(`u9`·`u10`·`u11`)이 evidence에 하나도 안 쓰였다.** 로그 범위를 전체 라운드로 넓힌 목적이 반쯤 안 살았다

### 진술대조권에는 있는데 키워드에 없는 것

진술대조 ②·④를 그대로 옮기면 되는 작업이다.

| | 키워드 | 진술대조 |
|---|---|---|
| 번호 검증 | ❌ `evidence: ["u99"]`도 통과 | ✅ `by_id` 밖은 버림 |
| `by_id` · 원문 치환 | ❌ `picked`를 버린다 | ✅ 있음 |
| 임계값 | ❌ 없음 (TC-9 미구현) | ✅ 3건·40자 |
| 회차 반복 | ❌ 1회 | ✅ `RUNS = 3` |
| 부분 문자열 검사 | ❌ 노트북에 없음 ([ai-lab](../ai-lab/src/main/java/com/ssafy/mafia/ailab/analysis/keyword/KeywordExtractService.java)에는 있다) | — |
| 프롬프트 규칙 | 6개 + 핵심 규칙 블록 | 3개 |
| `phase` | ❌ | ✅ |

**노트북이 Spring보다 방어가 약한 상태다.** 그리고 진술대조에서 축약이 효과를 봤으니 프롬프트 6개도 줄일 후보다.

### 붙일 순서

1. `by_id` + 번호 검증 — evidence로 원문을 찍어주면 오배정이 눈에 보인다
2. evidence **중복 배정 검사** — 같은 번호가 여러 키워드에 들어갔는지
3. `count == len(evidence)` 검사 — 위 결함이 1·2·3만으로 자동으로 걸린다
4. 임계값 (TC-9)
5. `phase` — 진술대조와 같은 이유로 필요할 수 있다

### 남은 결정 — 환각 방어를 어떻게 할지

`시간 남비`(STT 오인식)를 모델이 `시간 낭비`로 교정해서 내놓는다. **사람이 봐도 그게 맞는 해석이다.** 그런데 부분 문자열 검사를 그대로 쓰면 원문에 없으니 버려진다.

| | 검사 유지 | 완화 |
|---|---|---|
| 얻는 것 | 없는 말을 만드는 걸 확실히 막음 | STT 오인식 교정이 살아남 |
| 잃는 것 | **교정된 키워드가 전부 버려짐** | 지어낸 상위 개념어가 통과 |

`evidence` 번호를 받고 있으니 **키워드 문자열은 검사하지 않고 근거 번호만 검증**하는 중간 방법이 있다. 유저가 근거 발화를 함께 보므로 확인이 가능하다.

**진술대조 실측이 이 결정에 힌트를 준다** — 원문 인용을 금지하고 번호만 받는 쪽이 잘 작동했다. 키워드도 번호 검증에 무게를 두는 편이 일관된다.

## 확정된 사실 (참조용)

- **AI 심판 모델 = `gpt-5.4-mini`** — reasoning 모델의 "스트리밍 초반 침묵" 우려가 실측에서 나타나지 않았다(첫 글자 1.13초)
- **`gpt-5.x` 는 `max_tokens` 를 쓰면 HTTP 400** — `max_completion_tokens` 필수
- **`GET /models` 미지원** — 모델명을 API 로 발견할 수 없다. 확인된 것은 `gpt-4o-mini`, `gpt-5.4-mini`
- **조간신문 500자, 짧게만 보여주는 것은 의도된 설계** — 천천히 읽으면 게임이 쉬워진다. 프롬프트에 "중요한 정보를 앞쪽에 배치"를 지시해야 한다
- **글자수는 프롬프트로 안 지켜진다. `max_tokens`가 유일한 실효 상한이다** — 1토큰 ≈ 1.5자이므로 300이면 450자쯤에서 막힌다 (07-30 조간신문)
- **한 줄에 이름이 둘이면 모델이 주체를 뒤집는다** — 화자와 언급 대상이 같은 줄에 있으면 "밤하늘이 소금빵을 지적한 말"이 "소금빵이 경고했다"가 된다. `말한사람` · `발언` 라벨로 끊어서 고쳤다 (07-30, 2회 연속 관찰)
- **LLM 출력과 서버 조립을 시점으로 분리하면 조작을 구조로 막을 수 있다** — 조간신문 2단 조립. 밤에는 사망자 줄이 존재하지 않으므로 마피아가 처형·역할을 조작할 방법 자체가 없다
- **코드 스타일** — Lombok 사용, 패키지는 도메인별, `ChatClient` 는 빈 주입, LLM 출력 계약은 `record`, 프롬프트는 `.st` → [개발환경 §4-1](개발환경.md)
- **환각 방어는 기능마다 다르다** — 진술대조는 발화 번호 반환, 키워드는 부분 문자열 검사
- **`.options()` 는 Spring AI 2.0 에서 `Builder` 를 받는다** — `.build()` 를 붙이면 컴파일되지 않는다 (1.x 는 `ChatOptions`)
- **STT 는 브라우저에서 한다** — 화자 구분이 공짜로 되고, `confidence` 는 오인식 탐지에 쓸모가 없다 → [발화수집-STT.md](발화수집-STT.md)
- **발화별 판단은 안정적이고 조합 탐색은 불안정하다** — 여러 개를 놓고 조합을 훑는 것은 같은 입력에도 흔들린다 (8회 관찰). **다만 짝을 하나만 요구하면 안정적이었다** — 조합을 코드로 옮기기 전에 개수를 줄여보는 게 먼저다
- **규칙을 늘리는 것보다 입력을 고치는 쪽이 낫다** — 2026-07-29 진술대조에서 프롬프트 규칙 8개 → 3개로 줄였는데 성적이 올랐고, 판정을 바꾼 것은 입력 수정 세 개(대상 발화만 · 코드 컷오프 · `phase`)였다 → [진술대조 §2-3](../log_analysis/prompts/진술대조.md)
- **모델이 스스로 하는 것과 못 하는 것이 갈린다** — 의견 변화 vs 과거 진술 왜곡 구분, STT 깨짐 처리는 안 가르쳐도 한다. **마피아 추측 금지는 못 한다** (규칙을 빼면 "정체를 추론해드릴까요"라고 먼저 제안했다). 지시가 지켜지지 않는 규칙(같은 방향 짝짓기 금지)은 넣어도 값을 못 한다
- **서버가 아는 사실을 안 주면 모델이 추측하고, 추측은 과제 방향으로 기운다** — `phase`가 없으면 투표 선언("저는 X 씨입니다")을 정체 주장으로 읽어 없는 모순을 만든다. 투표 내역(TC-3)도 같은 계열이다
- **프롬프트에 "몇 시까지"를 글로 적으면 안 지킨다** — 서버가 잘라서 넘겨야 한다. 검증할 때는 **새 세션에서 돌린다** (같은 대화의 앞선 결과가 다음 답변에 새어든다)
