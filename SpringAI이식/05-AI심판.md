> 노트북: `# 4. AI 심판` 셀 4개
> 프롬프트: [ai-judge-system.st](prompts/ai-judge-system.st) · [ai-judge-user.st](prompts/ai-judge-user.st)
> 렌더 기준값: [렌더스냅샷/AI심판-R1-user.txt](렌더스냅샷/AI심판-R1-user.txt)

**마지막에 옮긴다.** `.stream()` 을 처음 쓰고, WS 이벤트 순서 보장이 얽힌다. 통계 6종 계산도 여기만 있다.

> ⚠️ **`ai-judge-system.st` 에 `{닉네임}` 이 들어 있다.** 마지막 문장 형식 지시다. 템플릿으로 렌더하면 이 지시가 사라지고, 그러면 `처형 대상은 OOO입니다.` 형식이 깨져서 파싱이 실패한다 → [00-코드스타일 §6](00-코드스타일.md).

## 1. 입력

### 서버가 조회하는 것 3개

1. **현재 생존자 목록** — 사망자는 처형 후보가 될 수 없다
2. **낮 공개 발화** — `utt:{roomId}:public`
3. **AI 심판 발동 시각** — 컷오프 기준 (시나리오1 은 `21:03:39`, `PHASE R1/AI_JUDGMENT`)

### LLM 에 넘기는 것 3개

1. 생존자 목록 (처형 후보)
2. **생존자별 발화 통계** ← 조회 2 에서 **계산**
3. 심판 발동 시각 **이전**의 낮 공개 대화

**조회 3(발동 시각)은 프롬프트에 넣지 않는다.** 1·2 의 컷오프 기준으로만 쓴다.

### 컷오프가 정답 유출을 막는다

`t < 심판 발동 시각` 으로 자르면 **심판 구간 발화 4건이 자동으로 빠진다.** 그것들은 심판 결과에 대한 반응이라 입력이 되면 정답이 새어 나간다.

**`phase` 화이트리스트는 두지 않는다.** 심판이 보는 것은 발화 리듬이라 시작 인사(`DAY_START`)도 재료다. 조간신문과 반대다.

실측 — R1 심판 `21:03:39` · 생존 6명 · 컷오프 이전 **25건 738자**.

### 🔴 역할을 넣지 않는다

절대 규칙 2. **칭호와 정반대다.** 심판은 발화만 보고 판단해야 한다. **정답률이 비정상적으로 높으면 유출을 의심한다.**

이벤트 파서가 `ROLE` 줄을 읽지 않게 한다 — 그 한 줄에 전원의 역할이 있다.

## 2. 통계 6종 — 서버가 세고 LLM 은 판결문만 쓴다

**발화 로그 하나에서 6종이 다 나온다. 별도 조회가 없다.**

| 통계 | 계산 |
|---|---|
| 발화 횟수 | 본인 발화 건수 |
| 총 글자 수 | 본인 발화 글자 합 |
| 전체 발화 비중 | 본인 글자 / **컷오프 이전 전원 글자** × 100 |
| 평균 발언 길이 | 본인 글자 / 본인 건수 |
| 라운드별 발화 횟수 | 라운드마다 건수 |
| 다른 참가자 이름 언급 횟수 | 본인 발화에서 **다른 참가자 이름 등장 횟수 합** (자기 이름 제외) |

### 정한 것 3개

| | |
|---|---|
| **비중 분모** | 컷오프 이전 **전원** 발화 글자수 (**사망자 포함**) |
| **`DAY_START`** | 포함 |
| **이름 언급** | 참가자 전원 이름, 자기 이름은 제외 |

### 통계는 생존자만, 낮 대화는 사망자 발화까지

**사망자는 판단 근거에 등장할 수 있지만 처형 대상은 될 수 없다.**

### 렌더 형식 — 프롬프트가 선언한 대로

```
라면왕
- 발화 6회, 총 128자
- 전체 공개 발화의 17.3%
- 평균 발언 길이 21.3자
- R1 6회
- 다른 참가자 이름 언급 1회
```

- 소수점 **1자리** (`17.3%` · `21.3자`)
- 라운드별은 ` / ` 로 연결 (`R1 6회 / R2 3회`)
- 플레이어 블록 사이는 **빈 줄 하나**

> 🔴 **소수점 자리수와 구분자가 어긋나기 쉽다.** 렌더 스냅샷과 비교하면 걸린다.

### 발화 렌더

```
[R1 시작 21:00:04] 라면왕: 이 시작했네요
[R1 토론 21:00:08] 라면왕: 자 첫 라운드니까 정보가 아예 없어요 …
```

`[R{round} {페이즈라벨} {t}] {speaker}: {text}` — 프롬프트가 선언한 형식이다.

> 조간신문에서는 이 형식이 주체를 뒤집었다(한 줄에 이름이 둘). 판결 이유에 "이 참가자"만 쓰게 되어 있어 영향은 작지만, **엉뚱한 사람의 특징이 근거로 적히는지 눈으로 확인한다.**

## 3. 프롬프트 — SYSTEM 1,930자

### 성격 — 진실 판정이 아니라 인상 평가다

> 당신의 임무는 실제 마피아를 정확히 찾아내는 것이 아니다.

**논리적 모순과 거짓말 검증은 진술대조권 몫이다.** 심판은 발화량·리듬·표현 반복만 본다. 프롬프트에 명시적으로 금지되어 있다.

```
- 발언 내용의 사실 여부를 판단하지 않는다
- 서로 다른 발언의 논리적 모순을 찾지 않는다
- 진술대조 분석처럼 과거 발언과 현재 발언을 논리적으로 비교하지 않는다
```

### 평가 기준 5종

발화 존재감 · **발화량 변화** · 표현 반복과 자기 정정 · 강한 표현과 방어적 반응 · 대화 리듬의 변화.

**적어도 두 가지 이상을 함께 고려하게 한다** — 발화량 하나만으로 선정하지 않도록.

### 관찰만 하고 단정하지 않는다

```
✗  "화를 냈다" "거짓말했다" "말을 더듬었다"
✓  "강한 표현이 늘었다" "같은 표현을 반복했다" "짧은 반박이 이어졌다"
```

### 🔴 판결문 형식이 계약이다

1. 관찰된 발화 특징을 차분하게
2. **정상적인 긴장이나 적극적 추리였을 가능성도 인정**
3. **마지막 문장에서만** 처형 대상 공개

```
처형 대상은 {닉네임}입니다.       ← 마지막 문장. 형식이 정확히 같아야 한다
```

- **판결 이유에 선정된 닉네임을 미리 밝히지 않는다** — "이 참가자", "해당 참가자"로 쓴다
- 판결 이유는 **3~5문장**
- 마지막 문장 뒤에 어떤 설명도 붙이지 않는다
- 제목·목록·JSON·마크다운 출력 금지

**출력이 평문 판결문이다. JSON 계약이 없다** — 칭호와 다른 점이다.

## 4. 파싱 + 검증

### 판결 이유와 대상을 분리한다

```
정규식:  처형 대상은\s*(.+?)\s*입니다\.?\s*$
→  (reason, target)
```

**여기서 실서비스의 스트리밍 계약이 정해진다** (§5).

### 검증 5종 — 계약 위반만 센다

| 검사 | 실패 조건 |
|---|---|
| 형식 | 마지막 문장이 `처형 대상은 OOO입니다.` 가 아니다 |
| **후보 검증** | `target` 이 생존자 목록에 없다 |
| 규칙 | 판결 이유에 `target` 이 미리 등장했다 |
| 길이 | 판결 이유가 3~5문장을 벗어났다 |
| 형식 | `#` · `**` · `{` · `- ` 흔적 (마크다운·목록·JSON) |

**후보 밖의 이름은 코드가 버린다.** 진술대조의 "없는 번호 버림"과 같은 계열의 환각 방어다 — 프롬프트를 어떻게 고쳐도 여기서 걸린다.

판결문의 톤과 설득력은 눈으로 본다.

## 5. 🔴 스트리밍 — 노트북에 없는 부분

노트북은 `.call()` 로 받아서 정규식으로 자른다. **실서비스는 `.stream()` 이다** (명세 20-5).

### 순서 보장이 계약이다

```
judgment.started   →  전원
judgment.reason    →  스트리밍 청크 (전원)
judgment.verdict   →  대상 확정 (전원)   ← 이유가 끝난 뒤 따로
judgment.failed    →  폴백
```

**"처형 대상은" 을 만나면 그 줄을 붙잡아 두고, 이유 출력이 끝난 뒤 별도 `judgment.verdict` 이벤트로 내보낸다.** 그래야 대상이 반드시 마지막에 열린다 — 연출이 성립하는 조건이다.

### 스트리밍이 성립하는 것은 확인됐다

`gpt-5.4-mini` 는 **reasoning 모델인데도 초반 침묵이 없다.** 첫 본문 글자가 **1.13초**에 나왔고 `gpt-4o-mini`(1.03초)와 거의 같다. 이 실측 때문에 심판에 `gpt-5.4-mini` 를 쓴다.

### 재접속 복구

심판 진행 중 재접속하면 **지금까지 스트리밍된 사유 전문**을 스냅샷으로 내려줘야 한다 → [AI-API명세 §4](참고/AI-API명세.md).

```jsonc
"judgment": { "inProgress": true, "reasonSoFar": "…", "verdict": null }
```

## 7. 알려진 한계

- **시나리오1 에서 AI 심판이 발동한 라운드는 R1 뿐이다.** R2·R3 은 최다득표가 나와 최후변론으로 갔다
- 그래서 **평가 기준 2(발화량 변화)를 판단할 재료가 없다.** 라운드가 하나뿐이다. **모델이 그것을 근거로 쓰면 없는 사실을 만든 것이다** — 검증할 때 이걸 본다
- 실제 서버 판정은 초코비였다(방어권으로 무효). 노트북 1회분은 **곰돌이**를 골랐다. 둘 다 오답이 아니다 — 진실 판정이 아니라 인상 평가이므로

## 8. 폴백

`judgment.failed` 를 내보내고 **게임 로직의 기본 처형 규칙으로 넘긴다.** 심판이 안 나왔다고 게임이 멈추면 안 된다.

방어권(`BOMB_DEFENSE`)은 패시브 아이템이라 심판 지목 뒤에 발동한다 — **AI 파트가 아니라 게임 로직 몫**이다. 심판은 대상만 정한다.
