## 0. 진술대조권과 무엇이 다른가

입력 소스(지목 대상의 발화)만 같고 나머지가 다르다. [§7-1](../../docs/AI기능-구현설계.md)

| | 진술대조권 | **키워드 뽑기** |
|---|---|---|
| 목적 | 발언 간 모순 탐지 (**추론**) | 무슨 말을 했는지 (**추출**) |
| 로그 범위 | 전체 라운드 | **현재 라운드만** ← 핵심 차이 |
| 역할 제한 | 시민만 | **전원** (마피아도 사용) |
| 모델 | `gpt-5.4-mini` | **`gpt-4o-mini`** — 토론 중 호출이라 가장 싸고 빠른 쪽 |
| temperature | — | **0** (창작이 아니라 추출) |

**현재 라운드로 제한하는 이유:** 전체 라운드를 보면 진술대조권과 산출물이 사실상 겹쳐서 아이템 두 개를 둘 이유가 없어진다. 라운드 간 변화는 진술대조권의 몫이다.

## 1. 입력을 만드는 규칙

| 항목 | 값 |
|---|---|
| 로그 소스 | `utt:{roomId}:public` **만** |
| 라운드 범위 | **현재 라운드만** |
| 화자 범위 | 지목 대상 1명의 발화만 |
| 시간 범위 | **아이템 사용 시각까지** |
| 역할 정보 | 넣지 않는다 |

시간 범위가 특히 중요하다. 아이템은 토론 중에 쓰이므로 그 라운드의 `DAY_START` + `DAY_DISCUSSION` 중 **사용 시각 이전** 발화만 존재한다. 이후 발화는 그 시점에 아직 없었다.

### 발화 임계값 — LLM을 호출하지 않는 조건

진술대조권과 같은 기준을 쓴다.

```
대상의 현재 라운드 발화가 3건 미만  또는  총 글자수 40자 미만  →  LLM 호출 없이 즉시 응답
```

**현재 라운드만 보기 때문에 진술대조권보다 임계값에 훨씬 자주 걸린다.** R1 토론 초반에는 대부분이 미달이다.

## 2. 출력 계약

```jsonc
{
  "hasFindings": true,
  "keywords": ["시간 낭비", "느낌", "억울", "시민"]   // 3~5개
}
```

발화가 부족할 때:

```jsonc
{ "hasFindings": false, "noFindingReason": "INSUFFICIENT", "keywords": [] }
```

`noFindingReason`: `INSUFFICIENT` (발화 부족). 화면 문구는 서버가 이 enum으로 고른다.

> 진술대조권과 달리 `NO_CONTRADICTION`에 대응하는 값이 없다. 발화가 임계값을 넘으면 뽑을 키워드는 반드시 있다.

**서버가 감싸는 부분** — `requestId`, `itemCode`, `targetPlayerId`. [AI-API명세 §2-5](../../docs/AI-API명세.md)의 형태와 일치한다.

### 환각 방어 — 원문 부분 문자열 검사

진술대조권은 발화 번호로 인용 환각을 막았다. 키워드는 성질이 달라서 **서버가 부분 문자열 검사로** 막는다.

```
각 키워드가 입력 발화 안에 실제로 등장하는 연속된 문자열인지 검사 → 아니면 버린다
비교 시 공백을 제거하고 맞춘다 ("시간낭비" ↔ "시간 낭비")
```

조사·어미를 떼는 것은 허용된다 — `억울하면` → `억울`은 부분 문자열이므로 통과한다. 반대로 로그에 없는 상위 개념어(`비협조`, `방어적`)는 통과하지 못한다.

**상위 개념어를 금지하는 이유:** 그것은 추출이 아니라 LLM의 해석이다. 해석이 섞이면 시민이 "AI가 그 사람을 비협조적이라고 판단했다"로 받아들이는데, 실제로는 아이템이 그런 판정을 하는 물건이 아니다.

## 3. 프롬프트

### System

```
당신은 마피아 게임의 발언 기록에서 특징적인 표현을 뽑아내는 분석관이다.
한 플레이어가 이번 라운드에 한 말을 받아서, 그 사람의 발언을 대표하는 표현을 골라낸다.

규칙:
1. 주어진 발언에 실제로 등장하는 표현만 고른다. 요약하거나 다른 말로 바꾸지 않는다.
   조사나 어미는 떼도 된다. 없는 단어를 만들어내면 안 된다.
2. 3개에서 5개를 고른다. 각 표현은 10자 이내로 짧게.
3. 그 사람의 태도나 입장이 드러나는 표현을 우선한다.
   누구나 쓰는 말("그러니까", "저는", "네")은 고르지 않는다.
4. 마피아인지 시민인지 추측하지 않는다. 판단하지 말고 뽑아내기만 한다.
5. 결과는 지정된 JSON 형식으로만 답한다.
```

규칙 1과 3이 이 프롬프트의 전부다. 1이 없으면 없는 단어를 만들고, 3이 없으면 의미 없는 조사·감탄사가 올라온다.

### User

```
분석 대상: {targetName}
라운드: {round}

이번 라운드 발언:
{utterances}
```

`{utterances}` 렌더링 — **번호를 매기지 않는다.** 진술대조권은 번호로 인용을 지목해야 했지만, 키워드는 번호가 필요 없다.

```
저는 그런 거 시간 낭비라고 생각해요 그냥 느낌으로 가야죠
아니 그러면 삼분 동안 뭘 어떻게 하겠다는 거예요 다들 시민이라고 할 거잖아요
...
```

## 3-1. 명세 변경 (2026-07-28) — 위 §0~§3 을 덮어쓴다

노트북에서 다시 설계했다. **위 내용과 `ai-lab` 구현은 아직 이 변경을 반영하지 않았다.**

새 명세는 이것이다.

> 현재 시점과 지목인을 받아, 대상 지목인의 **최초부터 지금까지의 발화**에서 반복적으로 등장한 키워드 5개를 추출한다. 완벽히 동일한 단어일 필요는 없고, **유사한 의미를 지닌 것은 하나로 처리**한다.

| | 기존 (§0~§3) | **변경** |
|---|---|---|
| 로그 범위 | 현재 라운드만 | **전체 라운드** |
| 개수 | 3~5개 | **정확히 5개** |
| 묶기 | 없음 | **의미로 묶는다** |
| 어미 | 원문 그대로 | **사전형으로 다듬는다** |
| 출력 | `keywords: []` | `keywords: [{keyword, evidence[]}]` |

### 로그 범위를 넓히면 진술대조권과 입력이 같아진다

§0 의 차별점("현재 라운드만")이 사라진다. 두 아이템이 **산출물로만** 구분되는 셈이다. [§7-1](../../docs/AI기능-구현설계.md)의 차별화 근거를 다시 볼 필요가 있다.

### "5개"와 "반복"이 데이터에서 충돌한다

한 사람의 발화 11건에서 **의미가 두 번 이상 반복되는 묶음은 1~2개뿐**이다. 3분 토론에서 같은 표현을 다섯 번 반복하는 사람은 없다.

첫 실행에서 키워드가 **1개만** 나왔다. 모델이 "반복해서 나온 것"을 성실하게 지킨 결과였다.

→ **"반복"은 고르는 우선순위로만 쓰고, 5개가 안 되면 한 번만 나왔어도 성격이 뚜렷한 표현으로 채우게 한다.** `count` 필드는 없앴다 — 요구하면 모델이 숫자를 지어낸다 (`count=3`인데 `evidence`가 2개인 사례).

### 의미로 묶는 것이 이 프롬프트의 핵심이다

딸기우유(딸기우유)의 발화를 보면 묶음이 실제로 다섯 개쯤 있다.

```
토론이 비효율적이다   ← 시간 낭비 / 삼분 동안 뭘 하겠나 / 방식이 비효율적
나는 결백하다        ← 억울하면 빠르게 / 숨길 게 없어요 / 진짜 시민이에요
남은 근거가 없다      ← 아무 근거도 없이 / 아무도 못 봤죠
상대 발언 차단       ← 그만 좀 하세요 / 조용히 좀 해봐요
느낌으로 판단        ← 그냥 느낌으로 가야죠
```

**"글자가 같은 반복만 세면 5개를 채울 수 없다"** 는 문장을 프롬프트에 명시해야 한다. 모델이 정확히 그 함정에 빠진다.

### 묶으라고 하면 요약 라벨이 나온다 — 반드시 막아야 한다

의미 묶기를 강조했더니 이런 게 나왔다.

```
소극적 태도      ← u5·u7 (원문에 흔적 없음)
지목 반박        ← u9   (원문에 흔적 없음)
근거 없는 주장    ← "아무 근거도 없이" 를 명사화
```

**5개 중 4개가 발화가 아니라 분석관이 붙인 라벨이었다.** 묶기와 원문 인용은 서로 반대로 당기는 힘인데, 묶기만 강조하면 묶음의 **이름을 요약해서 짓는 것**이 자연스러워진다.

이게 문제인 이유는 키워드 뽑기의 값어치가 **"그 사람이 실제로 한 말"** 을 보여주는 데 있기 때문이다. `소극적 태도`는 AI의 판단이지 증거가 아니고, 유저는 반박할 방법도 없다. 그리고 AI 심판·진술대조권과 성격이 겹쳐 세 아이템의 차별점이 사라진다.

→ 프롬프트에 **좋은 예·나쁜 예를 짝으로** 넣으면 걸러진다. 규칙만 쓰면 지켜지지 않는다.

```
나쁜 예: 소극적 태도      좋은 예: 숨길 게 없다
나쁜 예: 근거 없는 주장    좋은 예: 근거 없다
```

### 어미를 안 정하면 실행마다 문체가 바뀐다

```
1회차: 억울하다 / 숨길 게 없다 / 근거 없다        ← 다듬어진 형태
2회차: 억울하면 / 숨길 게 없어요 / 근거도 없이     ← 원문 그대로
```

같은 프롬프트인데 갈렸다. 비워두면 모델 입장에서 둘 다 맞다.

**경계는 "어미를 정리하는 건 허용, 단어를 새로 만드는 건 금지"다.** `억울하면 → 억울하다`는 같은 말을 다듬은 것이고 `소극적 태도`는 없던 말을 만든 것이다. 이 둘을 프롬프트에서 갈라줘야 문체가 고정된다.

### 남은 결정 — 환각 방어를 어떻게 할지

`시간 남비`(STT 오인식)를 모델이 `시간 낭비`로 **교정해서** 내놓는다. 사람이 봐도 그게 맞는 해석이다. 그런데 §2 의 부분 문자열 검사를 그대로 쓰면 원문에 없으니 **버려진다.**

| | 검사 유지 | 완화 |
|---|---|---|
| 얻는 것 | 없는 말을 만드는 걸 확실히 막음 | STT 오인식 교정이 살아남 |
| 잃는 것 | **교정된 키워드가 전부 버려짐** | 지어낸 상위 개념어가 통과 |

`evidence`로 발화 번호를 받고 있으니 **키워드 문자열은 검사하지 않고 근거 번호만 검증**하는 중간 방법이 있다. 유저가 근거 발화를 함께 보므로 확인이 가능하다. 어미를 다듬게 한 것도 부분 문자열 검사와 충돌한다(`억울하다`는 `억울하면`의 부분 문자열이 아니다) — 어간 비교로 완화하는 방법도 있다.

## 4. Spring AI로 옮길 때

- 출력 형식 지시는 `BeanOutputConverter`가 붙이므로 System 규칙 5번은 지워도 된다 → [LLM호출설정 §7](../../docs/LLM호출설정.md)
- `gpt-4o-mini`는 `max-tokens`를 쓴다 (`gpt-5.x`의 `max-completion-tokens`가 아니다). 키워드 몇 개라 낮게 잡으면 된다
- temperature 0
