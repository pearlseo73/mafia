## 0. 전제: 아키텍처 변경 사항

`시스템아키텍쳐.png`에 **Python/FastAPI 서비스가 없습니다.**

| 항목 | 초기 구상 (README) | 확정 아키텍처 |
|---|---|---|
| LLM 호출 | FastAPI → OpenAI/Anthropic | **Spring Boot → GMS (LLM API)** 직접 |
| STT | 서버 faster-whisper | **브라우저 Web Speech API** |
| 얼굴 분석 | 서버 or MediaPipe JS | **Vue + face-api.js** (명세 19-3 준수) |

## 2. 발화 로그 (Utterance) — 모든 LLM 기능의 공통 입력

### 2-1. 수집

- 브라우저 Web Speech API (`webkitSpeechRecognition`)로 **각 플레이어 클라이언트가 자기 음성만** 인식
- 인식 결과(`onresult`, final)를 플레이어 ID·시각과 함께 서버로 전송
- 발화 시각은 `onresult` 시점의 `Date.now()` → 실제 발화보다 수백 ms~1초 지연. 신문·진술 대조 용도로는 충분하나 **6-5 발화 테두리 판정에는 사용 불가**(그건 명세대로 클라이언트 오디오 레벨 분석 별도)

### 2-2. 저장: 키를 분리해서 격리

**하나의 리스트에 `visibility` 필드를 두고 조회 시 필터링하는 방식은 채택하지 않는다.** 언젠가 필터를 빼먹은 쿼리가 작성되고, 그것이 곧 마피아 신원 노출이다. 프롬프트에 들어갈 로그는 "가져오는 키가 애초에 다르다" 수준으로 막아야 실수가 구조적으로 불가능해진다.

```
utt:{roomId}:public       # 낮 시작/토론/투표/최후변론/AI심판 발화 (ZSET, score=timestamp)
utt:{roomId}:night        # 밤 마피아 발화 전체 (라운드는 레코드의 round 필드로 구분)
```

> **키 이름을 `:night` 로 통일했다 (2026-07-31).** 전에는 `utt:{roomId}:mafia:{n}` 이었다. 라운드별로 쪼개면 칭호가 밤 로그를 볼 때 라운드 수만큼 키를 순회해야 하고, [발화수집-STT §2](발화수집-STT.md) 의 "쪼개지 않는다"와 어긋난다. 레코드에 `round` 가 이미 있다.

| 소비자 | 접근 가능 키 |
|---|---|
| 조간신문 (17-1) | `:public` 만 |
| AI 심판 (20-2) | `:public` 만 |
| 진술대조권 (아이템) | `:public` 만 — 전체 라운드 |
| 키워드 뽑기 (아이템) | `:public` 만 — **전체 라운드** (2026-07-28 명세 변경) |
| 칭호 부여 (결산) | **`:public` 만** (2026-07-31 확정 — §2-3) |

- 조회 함수는 `getPublicUtterances(roomId)` 하나로 두고, mafia 키 접근 경로는 **결산 코드에만** 존재하게 한다.
- 칭호 부여는 게임 종료 = 역할이 이미 공개된 시점이므로 마피아 로그 사용이 유출이 아니다.

### 2-3. 밤 로그를 저장할 가치가 있는가

**저장하되 기대값은 낮게 본다.** 저장 비용은 사실상 0(같은 쓰기 경로 + 키 하나)이고, "낮에 동료 마피아를 팔아넘긴" 류의 칭호는 밤 로그 없이는 만들 수 없다. 다만 밤은 30초이고 21-4가 선착순 1명 지정이라 실제로는 한두 마디로 끝난다.

→ ~~칭호 프롬프트에서만 opt-in으로 포함~~ → **어느 LLM 프롬프트에도 넣지 않는다 (2026-07-31 확정).** 칭호가 밤 구간에서 쓰는 것은 **서버 이벤트(사망 라운드·원인)뿐**이고, 노트북 구현은 밤 대화 경로를 아예 선언하지 않았다.

근거 세 개다.

1. **얻을 것이 적다.** 픽스처의 밤 로그는 전체 **9건 197자**다. 30초 · 선착순 1명 지정이라 실제로 한두 마디로 끝난다
2. **경로가 있으면 실수가 가능해진다.** 낮 기능이 밤 키에 닿을 방법이 코드에 존재하지 않는 편이 프롬프트로 부탁하는 것보다 강하다 (§2-2 와 같은 논리)
3. **데이터 수집은 유지한다.** 저장 비용이 0이므로 나중에 [TC-27](테스트-체크리스트.md)로 효과를 재보고 싶어지면 그때 꺼낼 수 있다

밤 로그 경로가 노트북에 등장하는 유일한 곳은 **조간신문의 유출 검사**다 — 밤 문구가 출력에 섞였는지 문자열로 검사하는 용도이고 프롬프트 입력에는 닿지 않는다.

### 2-4. 보관 정책

- Redis 전 키에 TTL (게임 종료 + 여유 시간)
- **MySQL에 발화 원문을 저장하지 않는다.** 음성 유래 텍스트는 개인정보이므로 결과 집계(칭호, 승패, 통계)만 영구 저장
- Chrome Web Speech API는 온디바이스가 아니라 **오디오를 구글 서버로 전송**한다 → 개인정보 고지에 명시 필수

## 3. 얼굴 분석 (최후변론) — Vue 구현

### 3-1. 패키지 선택

**`@vladmandic/face-api`를 사용한다.** 원본 `face-api.js`(0.22.2)는 2020년 이후 방치되어 tfjs 1.7 고정 + ESM/Vite 번들링에서 깨진다. 위 포크는 API 호환 드롭인이며 tfjs 4.x · WebGL2 · Vite를 지원한다.

### 3-2. 모델 배치

CDN을 쓰지 않고 `public/models/`에 두어 Nginx가 정적 서빙한다(외부 의존·CORS 없음). **필요한 모델은 2개뿐이며 landmark68 / recognition은 로드하지 않는다.**

```
public/models/tiny_face_detector_model-weights_manifest.json + shard1   (~190KB)
public/models/face_expression_model-weights_manifest.json  + shard1     (~330KB)
```

### 3-3. 누가 계산하는가 (핵심 결정)

**최후변론 대상자 본인의 클라이언트가 자기 로컬 카메라 스트림으로 계산 → Spring Boot WS 전송 → 서버가 전원에게 브로드캐스트.**

근거:

- 19-1의 우측 패널은 **전원이 동일한 값**을 봐야 한다. 각자 수신 영상으로 계산하면 6명이 6개의 다른 동요 지수를 본다.
- CPU 비용이 1대에만 발생한다. 6명 전원이 추론하면 저사양 기기에서 LiveKit 프레임 드랍이 먼저 온다.
- 로컬 스트림이 SFU 수신 영상보다 화질·프레임레이트가 좋아 추론 품질도 우수하다.

리스크와 처리:

- 대상자가 브라우저를 조작해 값을 위조할 수 있으나, 이 지표는 19-4 찬반 투표에 직접 영향이 없는 **연출값**이므로 감수한다. 서버에서 `0~100` 클램프 + 초당 전송 횟수 제한만 적용.
- 대상자 캠 꺼짐/이탈 시 서버가 `status: UNAVAILABLE`을 브로드캐스트하고 6-4식 폴백 UI 표시.

### 3-4. 로딩 타이밍

모델 로드 + 첫 추론 워밍업이 수백 ms~1초다. **낮 투표(30초) 진입 시점에 미리 로드**한다. 최후변론 시작 후 로드하면 30초 중 초반이 빈 화면이 된다. 로드는 싱글톤 Promise로 감싸 중복 호출을 막는다.

### 3-5. 동요 지수 산식

프레임별 emotion 확률은 심하게 튀므로 그대로 쓰면 숫자가 춤춘다. 두 단계가 필요하다.

1. **EMA 스무딩** (alpha ≈ 0.15)
2. **베이스라인 보정** — 변론 시작 첫 3초 평균을 기준선으로 잡고 그 **대비 변화량**을 표시. "동요"는 절대값이 아니라 변화이므로 연출적으로도 유리하다.

```
raw = 0.35*fearful + 0.25*angry + 0.20*surprised + 0.15*sad + 0.05*disgusted - 0.30*neutral
```

### 3-6. composable 골격

```ts
// src/composables/useFaceAgitation.ts
import * as faceapi from '@vladmandic/face-api'

let modelsReady: Promise<void> | null = null
export function preloadFaceModels() {
  return (modelsReady ??= Promise.all([
    faceapi.nets.tinyFaceDetector.loadFromUri('/models'),
    faceapi.nets.faceExpressionNet.loadFromUri('/models'),
  ]).then(() => void 0))
}

export function useFaceAgitation() {
  const score = ref(0)
  const status = ref<'idle'|'loading'|'running'|'no_face'|'error'>('idle')
  let timer: number | null = null
  let ema: number | null = null
  let baseline: number | null = null
  const samples: number[] = []

  const opts = new faceapi.TinyFaceDetectorOptions({ inputSize: 224, scoreThreshold: 0.5 })

  async function start(video: HTMLVideoElement, onScore: (v: number) => void) {
    status.value = 'loading'
    await preloadFaceModels()
    await faceapi.detectSingleFace(video, opts).withFaceExpressions()  // 워밍업
    status.value = 'running'

    timer = window.setInterval(async () => {
      const r = await faceapi.detectSingleFace(video, opts).withFaceExpressions()
      if (!r) { status.value = 'no_face'; return }
      status.value = 'running'
      const e = r.expressions
      const raw = 0.35*e.fearful + 0.25*e.angry + 0.20*e.surprised
                + 0.15*e.sad + 0.05*e.disgusted - 0.30*e.neutral
      ema = ema === null ? raw : ema + 0.15 * (raw - ema)

      samples.push(ema)
      if (baseline === null && samples.length >= 30) {        // 첫 3초 = 베이스라인
        baseline = samples.reduce((a,b)=>a+b,0) / samples.length
      }
      const v = Math.round(Math.min(1, Math.max(0, (ema - (baseline ?? ema)) + 0.5)) * 100)
      score.value = v
      onScore(v)                                             // WS throttle은 호출부에서
    }, 100)                                                  // 10fps로 충분 (30초 = 300샘플)
  }

  function stop() {
    if (timer) clearInterval(timer)
    timer = null; ema = null; baseline = null; samples.length = 0
    status.value = 'idle'
  }
  onUnmounted(stop)   // 필수 — interval 누수 시 다음 라운드에 추론이 중복 실행됨
  return { score, status, start, stop }
}
```

### 3-7. 성능 튜닝 순서

1. 10fps 고정으로 시작
2. 프레임 드랍이 보이면 `inputSize`를 224 → 160으로 하향
3. Web Worker 도입은 **마지막 수단**. face-api.js는 `<video>` 엘리먼트를 직접 받으므로 Worker로 옮기려면 OffscreenCanvas 경로를 새로 작성해야 하고, 비용 대비 효과가 낮다

## 4. AI 심판 / AI 위임 (Task 20, 18-7·18-8)

### 4-1. 동작 정의

**18-7의 "AI 위임"과 Task 20의 "AI 심판"은 동일한 LLM 호출 하나다.** 위임한 인원 수만큼 호출하지 않는다.

- AI는 **누가 마피아이고 누가 시민인지 모른다.** 오직 밤을 제외한 시간의 발화 기록만 보고 의심자를 고른다.
- AI 심판이 발동하면 1회 호출로 처형 대상 1명이 결정된다 → 라운드당 비용 1회로 고정
- 20-6: 대상에게 방어권이 있으면 처형되지 않으며, 우측 분석 내용에 방어권 발동 안내

### 4-2. 스트리밍 구조

20-5가 "심판 사유를 먼저 나열한 뒤 마지막에 처형 대상 발표"이므로, **사유가 앞·판정이 뒤에 오는 단일 스트리밍 호출**과 구조가 정확히 일치한다. 연출 시간(20-4 얼굴 순차 표시)이 LLM 지연을 흡수한다.

- 소요 시간은 **약 30초**로 가정 (13-2에 AI 심판 구간이 누락되어 있으므로 명세 보강 필요)
- 서버는 스트리밍 종료 후 대상이 **생존 플레이어인지 검증**해야 한다 (사망자·미존재 ID 반환 방어)
- **타임아웃 폴백 필수**: LLM 실패/지연 시 규칙 기반(예: 발화량 최저 또는 지목당한 횟수 최다) 또는 무작위로 대체하고 시스템 알림 처리

### 4-3. 미결 사항 — 투표 집계 규칙

> 6명 중 1명만 A에게 투표하고 5명이 AI 위임한 경우, A가 최후변론인가 AI 심판인가?

**권고: "AI"를 하나의 후보로 취급한다.**

- 최다 득표가 AI → AI 심판
- 플레이어 간 동률 → AI 심판
- 단독 최다 플레이어의 표가 AI 위임 수보다 많음 → 최후변론

18-8의 "특정되지 않으면"이라는 표현과 부합하며, 다수가 위임했는데 1표짜리가 변론대에 서는 상황을 방지한다. **팀 확정 필요.**

## 5. 칭호 부여 (신규 Task 22)

### 5-1. 순수 LLM 창작을 피하는 이유

발화 로그만 주고 "칭호를 만들어줘"라고 하면 **팀킬하지 않은 사람에게 팀킬상을 준다.** 칭호의 재미는 사실관계가 정확할 때만 발생하고, 사실관계는 텍스트 추론이 아니라 서버가 이미 보유한 숫자에 있다.

### 5-2. 하이브리드 설계

1. **서버가 지표를 집계** (Redis 이벤트 로그 → 숫자)
   - 역할, 생존 여부
   - 총 발화 시간 / 횟수, 침묵한 라운드 수
   - 투표 내역 + 그 대상의 실제 역할 → **팀킬 횟수 / 적중 횟수**
   - 최후변론 찬반 이력
   - 아이템 사용 횟수, 지목당한 횟수
2. **LLM은 창작만 담당** — 지표 테이블 + 인상적인 발화 몇 줄을 입력받아 대사를 생성
3. **전원을 한 번의 호출로** 처리하고 JSON 배열로 수신 → 대사 톤이 서로 겹치지 않게
4. **서버 검증**: (a) 플레이어 ID가 실제 참가자인지 (b) 빈 항목이 없는지

### 5-3. 🔴 칭호명을 누가 정하는가 — B 안으로 확정 (2026-07-31)

| | 안 | |
|---|---|---|
| ~~A~~ | ~~LLM이 칭호명 + 대사를 함께 창작하고 중복을 스스로 회피~~ | **기각** |
| **B** | ****칭호예시.txt** 16종을 고정 세트로 두고 서버가 지표로 매칭. LLM은 대사만** | ✅ **채택** |

근거 세 개다.

1. **16종 중 10종이 이미 숫자로 정의돼 있다** — "발화량 1위", "시민인데 최다 지목", "동료에게 투표". 지표가 곧 칭호다
2. **중복·환각이 구조적으로 불가능해진다.** A안은 6명을 한 번에 요구해 중복 금지를 프롬프트에 부탁하는 구조인데, 이는 CLAUDE.md 의 "여러 개를 요구하면 흔들린다"와 정면으로 부딪힌다. 진술대조에서 배운 **"조합은 코드가 만들고 LLM은 문장만"** 을 적용하는 자리다
3. **폴백이 곧 본로직이 된다.** LLM이 죽어도 칭호는 나가고 대사만 기본 문구로 대체된다. 조간신문 2단 조립과 같은 성격이다

**출력 계약에서 `title` 이 입력으로 옮겨간다.** `title` 을 되받지 않으면 칭호 환각이 원천적으로 불가능하다 — 진술대조가 원문을 되받지 않는 것과 같은 방어다.

**B에서도 남는 문제** — 지표가 동점인 사람의 배정 규칙이다. 픽스처에서 곰돌이·라면왕이 투표 적중 3/3, 발화량 21건 vs 20건으로 갈리지 않는다. 타이브레이크 지표를 쓸지, 탐욕 배정할지, 애매한 사람만 LLM에게 후보를 주고 고르게 할지 정해야 한다 → **SpringAI이식/06 §8-3**

### 5-4. 비용·지연

게임당 1회 호출, 결산 화면은 2~5초 로딩을 허용할 수 있어 AI 기능 중 가장 부담이 적다. 실측 6.0초 · 입력 4,077토큰이라 **승패·역할을 먼저 띄우고 칭호를 나중에 채우는 구조**가 필요하다.

## 6. 조간신문 (Task 17)

**설계·실측 정본은 [조간신문.md](조간신문.md)다.** 여기는 다른 기능과의 접점만 남긴다.

- 생성 시점: **낮 결과 확정 직후** → 밤 시작 +5초에 조작권 소지자에게 표시(17-3) → 다음 낮 시작 시 전원에게 10초 표시(17-6)
  - 17-1(낮 투표 시작)에서 늦춘 것이다. 그대로 두면 **동률·AI 심판·방어권·밤 사망이 전부 신문 생성 뒤에 일어나** 어젯밤의 큰 사건이 신문에 안 들어간다 → 명세 수정 요청 항목
- 생성 가용 시간: **R1 4초 / R2 9초** (노출을 밤 시작 +5초로 둔 값). 이전에 적어둔 "60초 이상"은 17-1 기준이었다 → **워밍업 호출 필수**(첫 호출 4~7초)
- 입력: `utt:{roomId}:public` **만** + 낮 결과 한 줄. 역할·득표·발화 번호는 넣지 않는다
- 길이: `max_tokens=300`(≈450자)이 실효 상한이고 서버가 500자를 재검사한다. **프롬프트에 글자수를 적어도 지켜지지 않았다** (명세 17-2는 1000자 → 500자 수정 요청)
- **2단 조립** — 밤에는 머리글 + LLM 본문만, 아침에 서버가 사망자 줄(17-7)을 맨 앞에 붙인다. 밤에는 밤 살해가 아직 없어 그 줄을 만들 수 없고, 이 순서 덕에 **처형·역할 관련 조작이 구조적으로 무효화**된다
- 사전 열람은 **조작권 소지자 한 명만.** 마피아 전원에게 주면 시민이 상시 불리해진다
- 마피아 조작 아이템 `조간신문 조작권`(17-4·17-5): 편집은 상시 가능하나 **Apply를 눌러야** 최종 반영 + 아이템 사용 완료 처리
  - 아이템 상태표에 **"사용 중" 상태가 없다**(**아이템.png**) → 편집 UI를 열어둔 동안에도 아이템은 "사용 가능"이며 Apply 시점에 바로 "사용 완료"로 전이한다. 16-6의 롤백 대상이 아니다.
  - 편집 결과는 LLM을 다시 호출하지 않는다(텍스트 치환) → 길이 제한만 재검증
  - LLM 실패로 본문이 없으면 **아이템을 소모시키지 않는다**

## 7. AI 아이템 (Task 16)

출처: **아이템.png**

**LLM을 호출하는 아이템은 아래 두 개뿐이며, 게임상 별개의 아이템이다.**

| 아이템 | 대상 역할 | 유형 | 사용 시점 |
|---|---|---|---|
| **특정인 지목 진술대조권** | 시민 ONLY | Active | 토론 때 ONLY |
| **특정인 지목 키워드 뽑기** | ALL | Active | 토론 때 ONLY |

> `조간신문 조작권`(마피아, 밤)과 `AI 심판의 폭탄 방어권`(패시브)은 이름에 AI가 들어가지만 **LLM 호출이 없다** → AI 파트 산출물이 아니며 각각 §6·§4-1에서 다룬다. `자기 표 두표로 계산`, `원하는 사람 말 못하게 하기`도 범위 밖이다.

### 7-1. 두 아이템의 차별화

입력 소스(지목 대상의 발화 이력)만 같고 나머지는 다르게 설계한다. 같은 프롬프트에 출력 형식만 바꾸면 두 아이템이 사실상 동일해져 하나를 넣을 이유가 없어진다.

| | 진술대조권 | 키워드 뽑기 |
|---|---|---|
| 목적 | 발언 간 **모순·회피** 탐지 | 대상이 무슨 말을 했는지 **요약** |
| 로그 범위 | **전체 라운드** (라운드 간 말이 바뀌는 것이 핵심) | **현재 라운드** |
| 산출물 | 모순 지점 + 근거 인용 | 키워드 목록 |
| 역할 제한 | 시민만 | 전원 |
| 난이도·비용 | 높음 (추론) | 낮음 (추출) |

### 7-2. 지연이 게임 흐름에 직접 노출된다 (최대 리스크)

조간신문과 AI 심판은 **국면 전환 시점**에 호출되어 연출(13-3 fog, 20-4 얼굴 순차 표시)이 LLM 지연을 흡수한다. 그러나 이 두 아이템은 **3분 토론이 진행되는 중에** 호출되므로 지연이 그대로 유저에게 보인다.

- 목표 응답 시간을 정하고(키워드 뽑기는 특히 짧게), 초과 시 로딩 UI + 타임아웃 폴백을 둔다
- **토론 잔여 시간이 목표 응답 시간보다 짧으면 사용 자체를 차단**할지 결정 필요 (아이템을 소모했는데 결과를 못 보는 상황 방지)

### 7-3. 16-6 롤백 규칙의 공백

명세 16-6은 *"토론 중 아이템 사용 대상 지정 **대기 중**, 투표로 넘어간다면 대기 중이었던 아이템은 사용 취소 처리"*까지만 정의한다. **대상 지정은 완료되었고 LLM 호출이 진행 중인 상태에서 투표로 전환된 경우**가 정의되어 있지 않다.

**권고: 대상 지정 완료 = 사용 확정(사용 완료)으로 처리하고, 결과가 늦게 도착해도 표시한다.** 아이템을 소모했는데 결과가 사라지는 것이 유저 체감상 최악이다. 단 §7-2의 사전 차단과 함께 적용해야 한다.

### 7-4. 서버 측 검증 항목

- **요청자 역할 검증 필수** — 진술대조권은 시민 전용이므로 클라이언트 요청을 신뢰하지 않고 서버가 역할을 확인한다
- 지목 대상이 **생존 플레이어**인지 확인
- 16-9에 따라 **자기 자신 지목 허용** (액티브 && 사용자 지목 아이템)
- 16-7: 사용 중인 액티브 아이템이 있으면 거부
- 16-8: 현재 상태와 동일한 상태 변경 요청은 무시
- 16-10: 사망 시 보유 아이템 전부 사용 완료 처리 → 진행 중인 LLM 호출 결과는 폐기

### 7-5. 프롬프트 주의사항

**모순이 없으면 없다고 말하도록 강제해야 한다.** LLM에게 "모순을 찾아라"라고만 지시하면 침묵한 플레이어나 발언이 일관된 플레이어에 대해서도 억지 모순을 만들어낸다. 이것이 그대로 시민의 판단 근거가 되면 게임이 망가진다.

- "분석할 발언이 부족합니다" / "모순이 발견되지 않았습니다"를 **정상 출력으로 명시**
- 인용은 반드시 실제 로그의 발화에서만 (없는 발언 생성 금지)
- 발화 수가 임계값 미달이면 **LLM을 호출하지 않고** 서버가 부족 메시지로 응답 (비용·지연·환각 동시 절감)

### 7-6. 결과 공개 범위 — ✅ 확정

**아이템을 사용한 본인만 대상자의 분석 결과를 볼 수 있다.** 사용했다는 사실만 전체 공지한다(15-5).

- 전체 공개하면 시민 전용 아이템(진술대조권)의 정보 우위가 사라지고 마피아가 정보를 공짜로 받는다
- 구현: `item.analysis.result`를 **요청자 본인에게만** WS 전송 ([AI-API명세 §2-5](AI-API명세.md)) → WS 개별 전송 지원이 선결 조건
- 15-4/15-5에 이 내용이 없으므로 **기능명세서에 문구 추가가 필요하다** (§9 참조)

## 8. 최우선 검증 항목 (PoC)

**브라우저 STT와 LiveKit이 마이크를 동시에 사용할 수 있는지를 다른 무엇보다 먼저 검증한다.**

세 가지 리스크가 겹쳐 있다.

1. `webkitSpeechRecognition`은 `getUserMedia` 스트림과 별개로 자체 마이크에 접근한다. 대부분 환경에서 동시 동작하지만 일부 기기에서 충돌·에코·인식률 저하가 보고된다. **이것이 실패하면 조간신문·AI 심판·진술분석·칭호부여 전부가 무너진다.**
2. **Chrome/Edge 전용**이다. Firefox 미지원, Safari 부분 지원 → 지원 브라우저 명시 필요
3. 오디오가 구글 서버로 전송된다 → 개인정보 고지 필수. 네트워크 장애 시 로그 결손 처리 필요
4. `continuous` 모드도 자동 종료되므로 `onend`에서 **재시작 루프** 필요

### 권장 작업 순서

1. **STT × LiveKit 마이크 공존 PoC** ← 여기가 전제
2. `Utterance` 스키마 + Redis 키 구조 확정
3. **조간신문** (가장 독립적이고 프롬프트 검증 사이클이 빠름 → 로그 스키마를 나머지 기능이 재사용)
4. AI 심판 (스트리밍 + 폴백)
5. 얼굴 분석 composable
6. **키워드 뽑기** → **진술대조권** (가벼운 쪽부터) → 칭호 부여
