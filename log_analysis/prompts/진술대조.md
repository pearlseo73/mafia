## 0. 입력을 만드는 규칙 (프롬프트보다 이게 먼저다)

| 항목 | 값 | 근거 |
|---|---|---|
| 로그 소스 | `utt:{roomId}:public` **만** | 밤 로그가 섞이면 마피아 신원 노출 |
| 라운드 범위 | **전체 라운드** | 라운드 간 말이 바뀌는 것이 이 아이템의 핵심 ([§7-1](../../docs/AI기능-구현설계.md)) |
| 화자 범위 | **지목 대상 1명의 발화만** | 아래 참조 |
| 시간 범위 | **아이템 사용 시각 이전** (사용 시각 자체도 제외) | 그 이후 발화는 사용 시점에 존재하지 않았다. 제외 근거는 [§2-3 실측 3](#실측-3--시점을-글로-적으면-안-지킨다) |
| 페이즈 표시 | **넣는다** (`u12 [R2 투표 21:08:10]`) | 없으면 투표 선언을 정체 주장으로 읽는다 → [§2-3 실측 2](#실측-2--phase-가-tc-5-의-필요조건) |
| 역할 정보 | **넣지 않는다** | 마피아/시민을 알면 판정이 오염된다 |

**대상 1명의 발화만 주는 이유:** 전체 대화를 주면 LLM이 다른 사람의 발언을 대상의 발언으로 인용하는 실수가 생긴다. 애초에 대상의 발화만 넣으면 그 오류가 **구조적으로 불가능**해진다. [§2-2](../../docs/AI기능-구현설계.md)의 "가져오는 키가 애초에 다르다"와 같은 접근이다.

> **미결 1 → 기각 (2026-07-29).** 맥락을 덧붙이면 좋아질 것으로 봤으나 실측에서 **반대로 나왔다.** 전원 발화 65건을 주면 대상 발화 8건이 노이즈에 묻혀 오답이 난다. 맥락이 추가로 잡아준 모순도 없었다 → [§2-3 실측 1](#실측-1--맥락을-주면-나빠진다-미결-1-기각). **"회피" 탐지는 v0 범위 밖으로 유지한다.** 나중에 맥락이 필요해지면 발화 원문이 아니라 서버가 계산한 게임 상황 몇 줄을 주는 형태를 검토한다.

> **미결 2.** 투표 내역을 대조할지 (체크리스트 TC-3). "딸기우유에게 넣겠다"(21:01:12) ↔ 실제 `초코비→소금빵` 불일치는 발화 로그만으로는 검출 불가능하다. **v0에서는 넣지 않는다.**

### 발화 임계값 — LLM을 호출하지 않는 조건

[§7-5](../../docs/AI기능-구현설계.md)에 따라 서버가 먼저 걸러낸다.

```
대상의 발화가 3건 미만  또는  총 글자수 40자 미만  →  LLM 호출 없이 즉시 응답
```

응답은 `hasFindings: false` + `noFindingReason: "INSUFFICIENT"`. 소금빵/소금빵(2건·28자)이 여기서 걸린다.

> 소금빵은 **R1 밤 사망자**다. 실서비스에서는 임계값보다 먼저 [TC-7](../scenario/scenario1/테스트-체크리스트.md)(`TARGET_NOT_ALIVE`)로 막혀야 한다. 노트북에는 생존 검사가 없어 임계값까지 흘러가 우연히 같은 결과가 나온다 — 통과한 것이 아니다.
>
> `3`·`40`은 잠정값이다. R1 토론 중(`21:03:00`)에 쓰면 **6명 중 3명이 미달**이다 ([T8](../../docs/결정필요사항.md)).

## 1. 출력 계약 (LLM이 반환하는 JSON)

> **2026-07-29 축소됨.** 짝을 하나만 받기로 해서 `summary`와 `contradictions[]` 배열이 없어졌다. 현재 계약은 [§2-3 출력 계약](#출력-계약--summary-와-배열을-없앴다)이다. 아래는 여러 짝을 받던 형태의 기록이다.

**LLM은 발화 원문을 쓰지 않는다. 발화 번호만 반환하고 서버가 원문으로 치환한다.**

이게 인용 환각을 막는 가장 확실한 방법이다. 원문을 생성하지 않으면 없는 발언을 만들어낼 수 없다.

```jsonc
{
  "hasFindings": true,
  "summary": "한 문장. 무엇과 무엇이 충돌하는지만.",
  "contradictions": [
    {
      "utteranceIds": ["u2", "u6", "u9"],   // 서로 충돌하는 발화 2개 이상
      "reason": "왜 충돌하는지 한 문장"
    }
  ]
}
```

모순이 없을 때:

```jsonc
{ "hasFindings": false, "noFindingReason": "NO_CONTRADICTION", "contradictions": [] }
```

`noFindingReason`: `NO_CONTRADICTION` | `INSUFFICIENT`
→ 화면에 나갈 한국어 문장("모순이 발견되지 않았습니다" / "분석할 발언이 부족합니다")은 **서버가 이 enum으로 고른다.** LLM 문구를 그대로 쓰면 매번 표현이 달라진다.

**서버가 감싸서 내보내는 부분** (LLM은 모른다) — `requestId`, `itemCode`, `targetPlayerId`, 그리고 `utteranceIds` → `{round, time, text}` 치환.

> 이 때문에 [AI-API명세 §2-5](../../docs/AI-API명세.md)의 `contradictions[].quote`는 **LLM 출력이 아니라 서버 조립 결과**가 된다. 명세 주석 보강 필요.

## 2. 프롬프트

> **폐기 (2026-07-29).** 규칙 6개 → 8개(§2-1)로 늘렸다가 3개로 줄인 것이 성적이 더 좋았다. 현재 프롬프트는 [§2-3](#프롬프트--규칙-3개)이다. 아래는 규칙을 늘려가던 경과다.

### System

```
당신은 마피아 게임의 발언 기록을 검토하는 분석관이다.
한 플레이어의 발언 목록을 받아서, 서로 앞뒤가 맞지 않는 발언을 찾아낸다.

규칙:
1. 주어진 발언 목록 밖의 내용은 절대 사용하지 않는다. 추측하거나 보충하지 않는다.
2. 발언 원문을 다시 쓰지 않는다. 발언 번호(u1, u2 ...)로만 지목한다.
3. 모순이 없으면 없다고 답한다. 이것은 실패가 아니라 정상적인 결과다.
   억지로 모순을 만들어내는 것이 이 작업에서 가장 나쁜 실패다.
4. 판단 기준은 "같은 대상에 대한 태도·사실 주장이 서로 양립할 수 없는가"다.
   생각이 바뀔 수 있는 의견 변화와, 과거를 다르게 진술하는 것은 다르다.
   후자만 모순으로 본다.
5. 누가 마피아인지 추측하지 않는다. 발언 간의 일관성만 본다.
6. 결과는 지정된 JSON 형식으로만 답한다.
```

**규칙 4가 이 프롬프트의 핵심이다.** "생각이 바뀌었다"(마음이 바뀜)와 "과거를 다르게 말한다"(처음부터 믿었다 / 의심한 적 없다)를 구분하지 못하면, 정상적인 의견 변경까지 모순으로 잡아낸다.

### User

```
분석 대상: {targetName}

발언 목록 (시간순):
{utterances}
```

`{utterances}` 렌더링 형식 — 라운드는 반드시 표시한다. 라운드 간 변화가 판정의 근거다.

```
u1 [R1] 밤하늘 씨 말도 일리가 있어요 보통 마피아가 먼저 판을 짜려고 하니까
u2 [R1] 저는 딸기우유 씨가 제일 수상해요 아까부터 논의를 계속 막고 있어요 이번 투표는 딸기우유 씨한테 넣을 생각입니다
...
```

시각(`21:01:12`)은 넣지 않는다. 라운드만 있으면 충분하고, 초 단위 시각은 토큰만 쓴다. 서버가 `u2` → 시각을 되돌릴 수 있으므로 화면 표시에는 문제없다.

> **번복 (2026-07-29).** 현재는 **페이즈와 시각을 함께 넣는다** — `u12 [R2 투표 21:08:10] 저는 딸기우유 씨입니다`. 페이즈가 없으면 투표 선언을 정체 주장으로 읽어 TC-5가 깨진다([§2-3 실측 2](#실측-2--phase-가-tc-5-의-필요조건)). 대신 화자 이름을 뺐다(전부 대상이라 군말). 토큰 영향은 ±20 수준이다.

## 2-1. 실측 결과와 규칙 추가안 (2026-07-28) — ⬛ 폐기

> 여기서 추가한 규칙 6·7·8은 [§2-3](#2-3-확정-설계--짧은-프롬프트--입력-정제-2026-07-29)에서 전부 빠졌다. 규칙 6("같은 방향 짝짓기 금지")은 **넣어도 지켜지지 않았고**, 규칙 7이 덮으려 한 `u12` 오독은 프롬프트가 아니라 **페이즈 누락**이 원인이었다(§148의 추정이 맞았다). 아래는 그 경과 기록이다.

`ai-lab`에서 위 System 규칙 5개로 TC-1·2·4·5를 실제로 돌린 결과와, 거기서 나온 문제를 막으려고 **claude가 임의로 추가한 규칙 3개**다. **판정 기준은 설계 영역이므로 채택 여부를 사람이 정한다.** 아래 규칙은 현재 `statement-compare-system.st`에 들어가 있다.

### 규칙 5개로 돌렸을 때 (문서 원안)

**어제 🔴로 예상했던 실패는 일어나지 않았다.** "모순이 아니다"로 판정하는 문제는 재현되지 않았고, 3단 모순(`u2`·`u6`·`u9`)과 같은 라운드 자기모순(`u8`·`u9`)을 다 잡았다. `u5`("마음이 바뀐 겁니다")도 잡지 않았다. **라운드 표시 + 규칙 4가 원인이었다는 추정이 맞았다.**

남은 문제는 두 가지였다.

| 문제 | 실제 출력 |
|---|---|
| **중복 묶음** | `[u2, u6]`이 거의 같은 `reason`으로 두 번 나왔다. 기대답안은 2묶음인데 5묶음이 나왔다 |
| **거짓 양성** | `[u2, u8]` — u2("딸기우유가 제일 수상, 투표하겠다")와 u8("딸기우유 처형에 찬성했다")은 **같은 방향**이라 모순이 아니다. 규칙 3이 막아야 할 억지 모순이다 |

### 추가한 규칙 3개 (검토 대상)

```
6. 같은 방향의 발언끼리 짝지어서는 안 된다. 같은 대상을 둘 다 의심하는 발언끼리,
   또는 둘 다 신뢰하는 발언끼리는 모순이 아니다.
7. 발언의 뜻이 한 가지로 읽히지 않으면 모순으로 삼지 않는다.
   말을 줄여서 한 짧은 발언을 확대해석해서는 안 된다.
8. 같은 발언 묶음을 두 번 내지 않는다.
```

**중간에 실패한 표현도 기록해둔다.** 두 번 헛돌았고, 둘 다 한 쪽을 고치면 다른 쪽이 깨지는 형태였다.

| 시도한 표현 | 결과 |
|---|---|
| 규칙 6에 "**방향이 반대인 짝만 고른다**" + "묶음은 세 개까지" | 거짓 양성은 사라졌지만 **TC-2(`u8`↔`u9`)를 놓쳤다.** 개수 상한이 라운드 간 모순을 우선하게 만든 듯하다 |
| 규칙 7을 "**태도와 행동 진술이 어긋나는 것도 모순이다**" | TC-1·2는 완벽해졌지만 **TC-5가 깨졌다.** `u12`("저는 딸기우유 씨입니다" = 투표 선언)를 "내가 딸기우유가다"로 읽고 없는 모순을 만들었다 |

→ 두 번째 실패가 **입력 설계 문제**를 드러낸다. `u12`는 `DAY_VOTE` 페이즈의 투표 선언인데, 프롬프트에는 라운드만 있고 페이즈가 없어서 뜻이 한 가지로 읽히지 않는다. 규칙 7("확대해석 금지")로 덮었지만, **`u12 [R2/투표]`처럼 페이즈를 함께 넣는 편이 근본적일 수 있다.** 토큰이 늘고 다른 케이스에 미치는 영향은 확인하지 않았다. → 미결

> **해결 (2026-07-29).** 이 추정이 맞았다. 페이즈를 넣으면 `u12` 오독이 3/3 → 0/3으로 사라지고, 규칙 7 없이도 TC-5가 통과한다. 토큰 영향은 ±20이고 초코비(TC-1)는 망가지지 않았다 → [§2-3 실측 2](#실측-2--phase-가-tc-5-의-필요조건). **규칙으로 덮을 문제가 아니라 입력에 정보를 넣을 문제였다.**

### 아직 남은 노이즈

규칙 8개로도 **실행마다 거짓 양성 묶음이 한두 개 섞인다.** 예: `[u2, u7]`("딸기우유에게 넣겠다" ↔ "딸기우유한테 넣겠다" — 같은 방향인데 "입장을 뒤집었다"고 서술), `[u6, u9]`(reason이 순환 논리). 핵심 볼 포인트(3단 모순 검출 · `u5` 미검출)는 두 번 연속 통과했지만 **곁가지 묶음까지 깨끗해지지는 않았다.**

`temperature=0`인데도 실행마다 출력이 달라서([LLM호출설정 §3](../../docs/LLM호출설정.md)) 어느 표현이 효과가 있었는지 1회 실행으로는 판단할 수 없다. **프롬프트를 더 손볼 거라면 케이스마다 2회 이상 돌려서 비교해야 한다.**

### 출력 계약 쪽에서 조인 것

`reason` 산문이 `u9`를 언급하면서 `utteranceIds`에는 `u9`를 빼놓는 불일치가 나왔다. DTO 필드 설명(`@JsonPropertyDescription`)이 스키마로 실려 프롬프트가 되므로 거기서 막았다 — "reason에서 언급한 번호는 하나도 빠뜨리지 않는다".

### 서버가 처리하기로 한 것 (LLM에 맡기지 않음)

| 처리 | 이유 |
|---|---|
| 같은 번호 조합의 묶음 중복 제거 | 규칙 8로도 새는데, 화면에 같은 인용문이 두 번 뜨는 건 결정론적으로 막을 수 있다 |
| 범위 밖 번호(`u99`) 제거 | 환각 방어. 프롬프트 품질과 무관하게 보장돼야 한다 |
| 번호가 1개만 남은 묶음 제거 | 모순은 두 발언 사이에서만 성립한다. 남은 하나로는 화면에 보여줄 게 없다 |

겹치되 다른 묶음(`[u2,u6]`과 `[u2,u9]`)은 남긴다 — 3단 모순이 짝으로 쪼개진 정상 형태다(기대답안 볼 포인트 1).

## 2-2. 판정 B안 — LLM은 분류만, 조합은 코드가 (2026-07-28) — ⬜ 미착수·보류

> **구현하지 않았다.** §2-3에서 **짝을 하나만 받기로** 하자 흔들림 없이 TC-1·TC-2가 통과해서, 조합을 코드로 옮길 필요가 없어졌다. 아래 설계는 **여러 짝이 필요해질 때 꺼낼 카드**로 남긴다.
>
> 다만 §2-2의 8회 관찰은 **노이즈가 섞인 입력**(전원 발화 + 규칙 8개)에서 나온 것이다. 입력이 정제된 지금 여러 짝을 요구하면 다른 결과가 나올 수 있으므로, B안으로 가기 전에 §2-3 조건에서 한 번 다시 재야 한다.

§2-1 의 프롬프트를 **노트북에서 8회 돌려본 결과 방식 자체를 바꾸기로 했다.** 입력은 [STT 변형 픽스처](../scenario/scenario1/발화로그-공개-STT.jsonl)를 썼다 — 실제 서비스에 들어올 모양이다.

### 8회 관찰 — 무엇이 흔들렸는가

| 회차 | 결과 |
|---|---|
| 1 · 3 | 3~4개, 전부 정확 |
| 2 | 3개 중 1개가 **자기부정** — `reason`에 "모순이 아닙니다"라고 쓰고 목록에 담았다 |
| 4 | 1개, 정확 |
| 5 | 1개, **오답** (우호끼리 짝지음) |
| 6 | 2개 정확 (자기부정 2개는 서버가 버림) |
| 7 | **0개** — 우호끼리 하나만 찾고 그것도 스스로 false 표시 |
| 8 | 2개 정확 |

`temperature=0`이고 프롬프트·입력이 동일한데 **0~4개로 흔들린다.**

### 결정적 관찰 — 분류는 맞는데 짝을 안 만든다

7회차 로그가 원인을 보여줬다.

```
stances: u1 우호 / u2 적대 / u4 중립 / u5 우호 / u6 적대 / u7 적대 / u8 우호
contradictions: [u5, u8] 하나만          ← 우호끼리
```

`u2`가 `적대`로 정확히 분류돼 있다. 적대 셋 × 우호 둘이면 조합이 여섯인데 하나도 만들지 않았다. **인식 실패가 아니라 조합 탐색 실패다.**

**발화별 분류는 8회 전부 정확했다.** LLM은 하나씩 보는 판단은 안정적이고, 여러 개를 놓고 조합을 빠짐없이 훑는 건 불안정하다. 그러면 조합은 코드가 만들면 된다 — 적대 목록과 우호 목록을 곱하면 되고, 같은 입력이면 항상 같은 결과가 나온다.

### B안의 프롬프트 — 분류만 시킨다

발언마다 세 가지를 받는다. 짝짓기·중복 제거·`summary` 지시가 모두 빠져서 프롬프트가 절반으로 줄었다.

| 필드 | 내용 |
|---|---|
| `about` | 그 발언이 **누구에 대한** 말인지. **방 참가자 명단 중 하나**로 적게 한다 |
| `stance` | `적대` / `우호` / `중립` |
| `pastClaim` | 그 발언이 자기의 **과거 태도·행동에 대한 주장**인지 |

### 서버가 하는 판정

```
모순 = 같은 about  +  stance 반대(적대 ↔ 우호)  +  적어도 한쪽이 pastClaim
```

`pastClaim`이 규칙 4의 구분을 담당한다. 둘 다 현재 태도면 그냥 생각이 바뀐 것이므로 모순이 아니다.

| 짝 | 판정 |
|---|---|
| `u2`(적대, 현재) × `u5`(우호, **과거주장**) | ✅ 과거를 다르게 진술 |
| `u2`(적대, 현재) × `u8`(우호, **과거주장**) | ✅ 같음 |
| `u7`(적대, **과거주장**) × `u8`(우호, **과거주장**) | ✅ 같은 라운드 자기모순 |
| 적대 × 적대 | ❌ 같은 방향 |
| 적대(현재) × 우호(현재) | ❌ 단순 의견 변화 |

선별은 **라운드 간격이 큰 것 2개 + 같은 라운드 자기모순 1개**다. 성격이 다른 증거가 섞여 나가게 한 것이다. 프롬프트로 개수를 제한했을 때 중요한 것을 놓친 전례가 있어서(§2-1) 모델은 다 분류하게 하고 서버가 고른다.

### `about`에 명단을 주는 이유 — 이름 오인식 대응을 겸한다

STT가 `달기우유`·`딸기유유`로 이름을 갈라 적는다. 명단을 주고 "발음이 가장 비슷한 참가자로 정하라"고 하면 정규화가 분류 단계에서 끝난다. 서버가 편집거리로 교정하는 것보다 낫다 — LLM은 발음 유사도를 사람처럼 판단한다.

**역할(마피아/시민)은 절대 넣지 않는다.** 명단은 서버가 아는 정보지만 역할은 답을 알려주는 것이다.

### `reason`을 서버가 조립한다

```
딸기우유 씨에 대해 R1 의심함 → R3 과거에도 의심했다고 주장
```

내용은 바로 아래 인용문이 말하므로 라벨만 있으면 된다. **AI가 문장을 쓰지 않으니 지어낼 여지가 없다.** 자연스러운 문장이 필요하면 짝을 확정한 뒤 문장만 쓰는 호출을 하나 더 붙인다.

### B안에서 밟은 함정 — 되돌아갈 때 참고

B안 첫 실행에서 **전부 `중립`이 나왔다.** 원인은 프롬프트 설계 실수였다 — `분석 대상: 초코비`를 주고 "그 인물에 대한 태도"를 물어서, 초코비의 발언이 초코비에 대해 어떤 태도인지 분류하게 된 것이다. 전부 중립이 맞는 답이었다.

**대상이 두 종류인데 하나로 뭉갰다** — 검사하는 발화자와, 발언이 언급하는 인물(`about`). `about`을 추가하면 고쳐지지만, **그 수정 버전은 끝까지 확인하지 못했다.** B안으로 되돌아간다면 여기서부터 시작한다.

### A안에서 배운 것 — 되돌아갈 경우 참고

- **`isContradiction` 필드는 값어치가 있었다.** "모순 아님"을 목록에 담는 실패가 2회 중 1회 났지만 **자기평가 자체는 매번 정확했다.** 담을 자리를 주고 서버가 버리는 방식이 통했다
- **`summary`만 발화 번호 금지, `reason`은 허용.** reason에서 번호를 빼자 모델이 어느 발화를 다루는지 붙잡지 못해 개수가 1개로 줄고 오답이 났다. 심한 회차에는 인물 이름까지 "특정 대상"으로 뭉갰다
- 서버 필터 4종 — 없는 번호 · 모순 아님 표시 · 같은 방향(`stances` 기반) · 1개만 남은 묶음

## 2-3. 확정 설계 — 짧은 프롬프트 + 입력 정제 (2026-07-29)

노트북 [log_prompting.ipynb](../../log_prompting.ipynb) `# 2. 진술 대조`의 셀 5개가 정본이다. §2-1·§2-2를 대체한다.

### 결론

| | §2-1 (규칙 8개) | §2-3 (현재) |
|---|---|---|
| 프롬프트 규칙 | 8개 | **3개** |
| 짝 개수 | 여러 개 | **하나** |
| 입력 | 대상 발화 + 라운드 | 대상 발화 + 라운드 + **페이즈** |
| TC-1 | 통과 (곁가지 오답 섞임) | 통과 |
| TC-2 | 놓치는 회차 있음 | 통과 |
| TC-5 | 규칙 7로 간신히 | 통과 (페이즈로) |
| 토큰·응답 | — | 입력 535~676 · 1.0~2.4초 |

**규칙을 늘리는 것보다 프롬프트를 줄이고 입력을 고치는 쪽이 매번 효과가 컸다.** 오늘 세 번 같은 패턴이었다 — 노이즈(맥락 54건), 정답 유출(곰돌이 해설), 중의성(페이즈 누락). 셋 다 프롬프트가 아니라 입력 문제였다.

### 프롬프트 — 규칙 3개

System:

```
마피아 게임의 낮 발언 기록에서, 한 사람의 발언이 서로 앞뒤가 맞지 않는지 본다.

주어진 발언은 모두 분석 대상 한 사람의 것이고, 번호(u1, u2 ...)가 붙어 있다.

규칙:
1. 근거는 번호로만 답한다. 발언 원문을 다시 쓰지 않는다.
2. 누가 마피아인지 추측하지 않는다. 발언 간의 일관성만 본다.
3. 아래 JSON 형식으로만 답한다. 설명이나 코드블록 표시를 붙이지 않는다.
```

User:

```
{log}

분석 대상: {target}
모순이 있는 경우에만 서로 충돌하는 발언 번호 두 개를 답하시오.
```

**"모순이 있는 경우에만"이 빠지면 TC-5가 깨진다.** 명령형("번호 두 개를 답하시오")이면 모순이 없어도 두 개를 만들어낸다 — 사실상 §2-1이 금지한 "반드시 찾아라"가 된다.

**뺐는데 문제없던 규칙** — 모델이 안 배워도 한다:

| 뺀 규칙 | 근거 |
|---|---|
| 의견 변화 vs 과거 진술 왜곡 구분 (§2-1 규칙 4) | 라면왕에서 "판단 대상의 변경이지 말이 충돌하는 건 아니다"로 스스로 착지했다 |
| STT로 깨진 발화 처리 (§2-1 규칙 7 계열) | `u2`의 "너를 생각입니다"가 망가졌는데 "제일 수상해요"를 근거로 썼다 |
| 같은 방향 짝짓기 금지 (§2-1 규칙 6) | **넣어도 지켜지지 않았다.** 우호끼리 짝지은 회차가 나왔다 |
| 중복 묶음 금지 (§2-1 규칙 8) | 짝이 하나라 해당 없음 |

**남긴 규칙의 근거:**

- 규칙 1은 **계약**이다. 규칙 없이 자유 텍스트로 돌렸을 때 `u2` 인용의 뒷부분을 조용히 잘라냈다 — "근거 문장"이라며 원문과 다른 문장을 보여준 셈이다
- 규칙 2는 **모델이 스스로 못 한다.** 규칙 없이 돌렸을 때 답변 끝에 "초코비의 정체가 마피아일 가능성까지 추론해드릴게요"라고 먼저 제안했다. 절대 규칙 2 위반 직전이고, 작업을 범인 찾기로 이해했다는 신호다

### 실측 1 — 맥락을 주면 나빠진다 (미결 1 기각)

대상 초코비, `now` = 21:11:05, 각 조건 3회.

| 입력 | 토큰 | 3회 결과 |
|---|---|---|
| 전원 발화 65건 | 2415 | 3회 정답 — **단, 곰돌이 해설 덕** |
| 해설 3건만 제거 (62건) | 2282 | **3회 전부 오답** |
| 대상 발화 8건만 | 535 | **3회 전부 정답** |

곰돌이 해설 = 초코비의 모순을 옆에서 짚어주는 발화 3건이다.

```
21:05:58  어제 초코비 씨는 딸기우유 씨한테 투표한다고 했는데 실제로는 소금빵 씨한테 넣었어요   (TC-3)
21:06:30  방금 그 말 어제랑 완전히 다르잖아요 어제는 제일 수상하다고 했어요                  (TC-1)
21:10:58  방금 스스로 모순이잖아요 의심한 적 없는데 처형에 찬성했다고요                      (TC-2)
```

해설이 있으면 정답이 나오지만 **그건 찾은 게 아니라 읽은 것이다.** 해설만 빼면 맥락 54건은 노이즈로만 작동해 `u1`(밤하늘 얘기)·`u4`(자기 변호)처럼 딸기우유와 무관한 발화를 `u8`과 짝지었다. 3회차 `reason`은 문장 자체가 성립하지 않았다("u4에서는 딸기우유를 의심하지 않는다고 볼 수 없는데") — **억지로 짜맞춘 흔적**이고 체크리스트가 "가장 위험한 실패 모드"로 적은 그것이다.

번호를 대상 발화에만 붙여 **남의 발화를 근거로 낼 수단**은 막았지만, **읽고 답을 아는 것**은 막지 못했다. 셋 중 대상 발화만 주는 조건이 유일하게 깨끗하다.

맥락이 추가로 잡아준 모순은 하나도 없었다 — TC-2와 `u5`×`u6`은 65건 조건에서도 안 나왔다.

**실서비스 함의:** `21:11:20`(아이템 결과를 읽어주는 대사) 같은 발화는 픽스처 장식이 아니라 실제로 생긴다. 전원 발화를 주면 같은 대상을 다시 대조할 때 **이전 결과를 복창**하게 되고, 결과를 거짓으로 전달한 경우 그 거짓을 근거로 삼는다. 대상 발화만 주면 이 경로가 원천적으로 막힌다.

### 실측 2 — phase 가 TC-5 의 필요조건

대상 라면왕(모순 없는 인물), 각 조건 3회.

| 프롬프트 | phase 없음 | phase 있음 |
|---|---|---|
| 명령형 "번호 두 개를 답하시오" | `u12` 오독 3/3 | 오답 3/3 (`u2`×`u14` 등) |
| 조건형 "모순이 있는 경우에만" | `u12` 오독 3/3 | **모순 없음 3/3** ✅ |

```
u12 [R2 21:08:10] 저는 딸기우유 씨입니다      ← DAY_VOTE. "딸기우유에게 투표한다"
```

페이즈가 없으면 모델이 "나는 딸기우유다"라는 정체 주장으로 읽고, `u4`("딸기우유 씨 반응 속도가 빠르네요")나 `u14`("남은 마피아는 셋 중에 있어요")와 모순이라고 답한다. **라면왕이 하지 않은 주장을 만들어낸 뒤 그것과 모순을 찾은 것**이다.

STT 탓이 아니다. 원본 픽스처도 같은 문장이고, 같은 라운드에 명시형과 생략형이 섞여 있다.

```
21:07:45  저는 곰돌이 씨에게 투표하겠습니다     ← 명시형
21:08:10  저는 딸기우유 씨입니다               ← 생략형   ← 여기서 걸린다
21:08:20  저도 딸기우유 씨한테 넣겠습니다        ← 명시형
```

주어·조사 생략이 흔한 한국어에서 자연스러운 변이다. 문장만으로는 두 해석을 가릴 수 없고, **모델은 과제 방향(모순 찾기)에 부합하는 해석으로 기운다.** `[투표]`는 그 기울기를 이길 근거가 된다 — 투표 단계에서 이름을 말하는 것은 투표 행위라는 게 게임 규칙이고 모델은 그 룰을 안다.

**두 변경이 서로 다른 문제를 고친다.** 페이즈는 오독을, 조건형은 "없을 때 없다고 말하는 능력"을 담당한다. 하나만 넣으면 TC-5가 깨진다.

정확히 말하면 페이즈가 판단력을 올린 게 아니라 **함정 하나를 없앤 것**이다. 라면왕 발화 15건에 실제 모순은 없고 `u12`가 유일한 후보였다. 그것이 정상적으로 읽히자 만들 짝이 없어져 정직하게 "없음"을 냈다.

초코비는 두 조건 모두 3/3 `u2`×`u5`로 **되던 케이스가 망가지지 않았다.**

→ **`phase`를 Redis 저장 시 붙여야 한다.** 서버가 이미 아는 정보라 비용이 0이다. [AI-API명세 §5-3](../../docs/AI-API명세.md)으로 요청.

### 실측 3 — 시점을 글로 적으면 안 지킨다

프롬프트에 "21:11:05까지"라고 적었는데 모델이 `21:11:20`을 인용했다. 그 발화가 하필 **진술대조 결과를 읽어주는 대사**여서, 모순을 찾은 게 아니라 답을 읽은 상태가 됐다.

→ 서버가 잘라서 넘긴다. `t < now`로 **`now` 자체도 제외한다** — `21:11:05`는 "초코비 씨 진술 대조해볼게요"라 지목 대상을 먼저 알려준다.

앞 대화 맥락이 있는 상태에서 더 심했다. 같은 세션에서 초코비를 먼저 분석하면 그 결과가 컨텍스트에 남아 다음 답변에 다시 나온다. **프롬프트를 검증할 때는 새 세션에서 돌린다.**

### 출력 계약 — summary 와 배열을 없앴다

```jsonc
// 모순을 찾았을 때
{"hasFindings": true, "ids": ["u2", "u5"], "reason": "한 문장"}

// 없을 때
{"hasFindings": false, "ids": [], "reason": ""}
```

- `summary` 제거 — 짝이 하나라 `reason`과 중복이다
- `reason`은 **LLM이 쓴다.** §2-2의 "서버가 조립한다"는 판정 B안 전제이므로 지금은 해당 없음
- `hasFindings: false` + `reason == "INSUFFICIENT"`로 **임계값 차단과 모순 없음을 구분**한다. 화면 문구가 달라야 한다("분석할 발언이 부족합니다" / "모순이 발견되지 않았습니다")

서버 검증 3종:

| 검증 | 이유 |
|---|---|
| `by_id` 밖의 번호 제거 | 환각 방어. 프롬프트 품질과 무관하게 보장된다 |
| 남은 번호가 2개 미만이면 `hasFindings=false` | 모순은 두 발언 사이에서만 성립한다 |
| JSON 파싱 실패 → `null` | 폴백 판단용 |

### 3케이스 성적

| 대상 | 발화 | 결과 | 체크리스트 |
|---|---|---|---|
| 초코비 | 8건 289자 | 모순 있음 — `u2`×`u5` 또는 `u7`×`u8` | TC-1 · TC-2 |
| 라면왕 | 15건 317자 | 모순 없음 (1.2초) | TC-5 |
| 소금빵 | 2건 28자 | `INSUFFICIENT`, **호출 없음** | TC-4 |

소금빵은 코드가 막은 것이라 **프롬프트를 검증하지 않는다.** 프롬프트 성능을 말해주는 건 초코비와 라면왕 둘이다.

### 남은 것

- **짝이 하나만 나온다.** `u5`×`u6`("처음부터 믿었습니다" → 2분 뒤 그에게 투표)은 유효한 후보인데 안 나온다. 여러 개를 요구하면 흔들릴지 **재봐야 한다** — §2-2의 8회 관찰은 노이즈 조건이었으므로 정제된 입력에서는 다를 수 있다
- **어느 짝이 나올지는 회차마다 다르다.** 셋 다 정답이지만 재현되지 않는다. 같은 대상을 두 번 대조하면 다른 답이 나온다. 유저 입장에서 `u7`×`u8`(25초 간격 정면 자기모순)이 `u2`×`u5`("마음이 바뀐 겁니다"라는 해명이 붙어 반박 가능)보다 강하므로, 어느 것을 낼지 고르고 싶으면 판정 B안이 필요하다
- **생존 검사(TC-7) 미구현** — 노트북에 없다
- **투표 내역(TC-3) 미구현** — 미결 2 유지. `phase`와 같은 성격의 "서버가 아는 사실"이라 함께 검토할 가치가 있다

## 3. Spring AI로 옮길 때 주의

- Spring AI `PromptTemplate`의 기본 델리미터가 `{}`다. **위 JSON 예시를 `.st` 파일에 그대로 넣으면 중괄호가 변수로 해석돼서 깨진다.** 출력 형식 지시는 `BeanOutputConverter`에 맡기고 프롬프트 본문에서 빼거나, 델리미터를 바꿔야 한다.
- `BeanOutputConverter`는 자체 형식 지시문을 프롬프트 뒤에 덧붙인다. 위 System 규칙 6번과 중복되면 지워도 된다.
- temperature는 **낮게**(0~0.2). 창작이 아니라 판정이다.
