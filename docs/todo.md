## 🔜 내일 첫 작업 — 진술대조권 B안이 실제로 동작하는지 확인

노트북에서 **판정 방식을 통째로 바꾸는 중이었고, 마지막 확인이 안 끝났다.**

### 왜 바꿨는가

8회 돌려본 결과가 이렇다. 같은 프롬프트인데 흔들린다.

| 관찰 | 내용 |
|---|---|
| **발화별 판단은 안정적** | 태도 분류(적대/우호/중립)는 8회 전부 정확했다 |
| **조합 탐색은 불안정** | 같은 분류를 갖고도 모순 짝을 0~4개로 만든다. 적대 3개·우호 2개가 분류돼 있는데 우호끼리 하나만 짝지어 낸 회차도 있다 |

→ **조합은 코드가 만들면 매번 같은 결과가 나온다.** 그래서 LLM은 분류만 하고 짝짓기는 서버가 하는 구조(B안)로 바꿨다.

### 막힌 지점

B안 첫 실행에서 **전부 `중립`으로 나왔다.** 원인은 프롬프트 설계 실수였다 — `분석 대상: 초코비`를 주고 "그 인물에 대한 태도를 분류하라"고 했다. 초코비의 발언이 초코비에 대해 어떤 태도인지 물은 셈이라 전부 중립이 맞다.

**대상이 두 종류인데 하나로 뭉갰다.**

- 검사하는 사람 = 발화자 (초코비)
- 발언이 언급하는 사람 = `about` (딸기우유)

그래서 발언마다 `about`을 같이 받고 서버가 같은 인물끼리만 짝짓도록 고쳤다. 이때 **방 참가자 명단을 프롬프트에 넣어** `달기우유`·`딸기유유`를 `딸기우유`로 정규화하게 했다 — 이름 오인식 대응까지 겸한다.

**그 수정 버전을 돌렸을 때도 전부 `중립`이 나왔는데, 출력에 `about` 열이 없었다.** 새 셀 ④는 `u1 R1 밤하늘 우호` 형태로 찍혀야 한다. 셀 ②·③·④ 중 일부만 교체됐거나 재실행이 안 된 것으로 보인다.

### 그래서 내일 할 일

1. **노트북 커널 재시작 후 위에서부터 전부 실행한다.** 공통 셀(설정·로그읽기·strip_fence) → 키워드 → 진술대조 순서
2. 분류 표에 `about` 열이 나오는지 확인한다. `u2`가 `딸기우유 / 적대`, `u5`·`u8`이 `딸기우유 / 우호 / 과거주장`으로 나오면 정상이다
3. 그러면 짝은 **반드시** `u2↔u5`·`u2↔u8`이 나온다. 코드가 만드니까
4. **2회 이상 돌려서 같은 결과가 나오는지 확인한다.** B안의 목적이 그것이다
5. 분류가 흔들리면 그때는 다른 처방이 필요하다 — 분류는 8회 동안 안정적이었으므로 그럴 가능성은 낮다

### B안 판정 규칙 (코드가 하는 일)

```
모순 = 같은 about  +  stance 반대(적대↔우호)  +  적어도 한쪽이 pastClaim
```

`pastClaim`이 "의견 변화"와 "과거 진술 왜곡"을 가른다. 둘 다 현재 태도면 그냥 생각이 바뀐 것이다.

선별은 라운드 간격이 큰 것 2개 + 같은 라운드 자기모순 1개. 성격이 다른 증거가 섞여 나가게 한 것이다.

## 진술대조권 — 확정된 것과 미결

### 확정

- **LLM은 분류만, 조합은 코드가** (B안). 근거는 위 8회 관찰
- **`reason`은 서버가 기계적으로 조립한다** — `딸기우유 씨에 대해 R1 의심함 → R3 과거에도 의심했다고 주장`. AI가 문장을 쓰지 않으니 지어낼 여지가 없다. 내용은 바로 아래 인용문이 말한다
- **방 참가자 명단을 프롬프트에 넣는다.** 서버가 아는 정보라 비용이 0이고, 이름 오인식 정규화를 겸한다. **역할(마피아/시민)은 절대 넣지 않는다**
- **프롬프트에 "반드시 최소 1개는 찾아라"를 넣지 않는다.** 규칙 3과 충돌하고, 모순이 없는 사람을 지목했을 때 억지 모순을 만든다. 없을 때 없다고 하는 능력을 잃으면 아이템 자체를 못 믿게 된다

### A안(폐기 후보)에서 배운 것 — 되돌아갈 경우 참고

프롬프트가 짝짓기까지 하던 버전이다. 실측 이력은 [프롬프트 §2-1·§2-2](../log_analysis/prompts/진술대조.md)에 있다.

- **`isContradiction` 필드는 값어치가 있었다.** 모델이 "모순 아님"을 목록에 담는 실패가 2회 중 1회 나왔는데, 자기평가 자체는 매번 정확했다. 담을 자리를 주고 서버가 버리는 방식이 통했다
- **summary만 발화 번호 금지, `reason`은 허용.** reason에서 번호를 뺐더니 모델이 어느 발화를 다루는지 붙잡지 못해 판정이 나빠졌다 (개수 1개로 줄고 오답 발생)
- 서버 필터 4종 — 없는 번호 · 모순 아님 표시 · 같은 방향 · 1개만 남은 묶음

### 미결

- **`u2`가 STT로 깨진 상태에서 불안정하다.** `달기우유`·`너를 생각입니다`. B안의 명단 주입으로 해결되는지가 내일 확인 대상이다
- **`21:06:20` 병합 문제** — 해명("마음이 바뀐 겁니다")과 모순("처음부터 믿었습니다")이 한 발화다. 잡으면 정답과 오답이 동시에 성립한다. 프롬프트로 풀 문제가 아니다 → [발화수집-STT §5](발화수집-STT.md)
- **`reason`을 자연스러운 문장으로 할지.** 지금은 기계적 라벨이다. 필요하면 짝을 확정한 뒤 문장만 쓰는 호출을 하나 더 붙인다

## 키워드 뽑기 — 명세가 바뀌었다

오늘 노트북에서 다시 설계했다. 기존 [프롬프트 문서](../log_analysis/prompts/키워드뽑기.md)와 `ai-lab` 구현이 이 변경을 아직 반영하지 않았다.

| | 기존 | **오늘 확정** |
|---|---|---|
| 로그 범위 | 현재 라운드만 | **전체 라운드** (처음부터 사용 시점까지) |
| 개수 | 3~5개 | **정확히 5개** |
| 묶기 | 없음 | **의미로 묶는다.** 글자가 달라도 같은 태도면 하나로 |
| 어미 | 원문 그대로 | **사전형으로 다듬는다** (`억울하면` → `억울하다`) |
| 금지 | 상위 개념어 | **요약 라벨 금지** (`소극적 태도`, `근거 없는 주장`) |
| 근거 | 없음 | `evidence`로 발화 번호를 받는다 |

**로그 범위를 전체로 넓히면 진술대조권과 입력이 같아진다.** 산출물(키워드 vs 모순)로만 구분되는 셈이다. [§7-1](AI기능-구현설계.md)의 차별화 근거를 다시 볼 필요가 있다.

### 남은 결정 — 환각 방어를 어떻게 할지

`시간 남비`(STT 오인식)를 모델이 `시간 낭비`로 교정해서 내놓는다. **사람이 봐도 그게 맞는 해석이다.** 그런데 부분 문자열 검사를 그대로 쓰면 원문에 없으니 버려진다.

| | 검사 유지 | 완화 |
|---|---|---|
| 얻는 것 | 없는 말을 만드는 걸 확실히 막음 | STT 오인식 교정이 살아남 |
| 잃는 것 | **교정된 키워드가 전부 버려짐** | 지어낸 상위 개념어가 통과 |

`evidence` 번호를 받고 있으니 **키워드 문자열은 검사하지 않고 근거 번호만 검증**하는 중간 방법이 있다. 유저가 근거 발화를 함께 보므로 확인이 가능하다.

## 결정이 필요한 것

### 게임 기획 쪽

- **R1 토론에서 진술대조권을 막을지** — 임계값(3건·40자) 기준으로 R1 토론 종료 시점에 6명 중 3명이 미달이고, 통과해도 대조할 이전 라운드가 없다. 버튼을 비활성화할지, 눌리게 두고 "발언 부족"으로 아이템을 소모시킬지(후자는 아이템 낭비)
- **투표 내역을 진술대조 프롬프트에 넣을지** — 체크리스트 TC-3(말과 행동 불일치)은 발화 로그만으로는 검출 불가능하다. v0 에서는 넣지 않음
- **대화 맥락을 넣을지** — 대상 1명의 발화만 주면 "회피" 탐지가 안 된다. [§7-1](AI기능-구현설계.md)은 목적을 "모순·**회피**"로 적고 있다. v0 에서는 모순만 봄
- **첫 호출 워밍업을 둘지** — 아이템 2종은 토론 중 호출이라 첫 호출 4~7초가 유저에게 그대로 보인다. [T8](결정필요사항.md) 임계값과 함께 결정

### 픽스처 정리 — 기대답안 확정 전에 필요

- **체크리스트 TC-8 의 근거 발화 하나가 사용 시각 이후다.** `21:02:58` "근거도 없이"는 아이템 사용(`21:02:09`) 다음이라 입력에 들어갈 수 없다 → 근거 목록을 3개로 수정

## 확정된 사실 (참조용)

- **AI 심판 모델 = `gpt-5.4-mini`** — reasoning 모델의 "스트리밍 초반 침묵" 우려가 실측에서 나타나지 않았다(첫 글자 1.13초)
- **`gpt-5.x` 는 `max_tokens` 를 쓰면 HTTP 400** — `max_completion_tokens` 필수
- **`GET /models` 미지원** — 모델명을 API 로 발견할 수 없다. 확인된 것은 `gpt-4o-mini`, `gpt-5.4-mini`
- **조간신문 500자, 짧게만 보여주는 것은 의도된 설계** — 천천히 읽으면 게임이 쉬워진다. 프롬프트에 "중요한 정보를 앞쪽에 배치"를 지시해야 한다
- **코드 스타일** — Lombok 사용, 패키지는 도메인별, `ChatClient` 는 빈 주입, LLM 출력 계약은 `record`, 프롬프트는 `.st` → [개발환경 §4-1](개발환경.md)
- **환각 방어는 기능마다 다르다** — 진술대조는 발화 번호 반환, 키워드는 부분 문자열 검사
- **`.options()` 는 Spring AI 2.0 에서 `Builder` 를 받는다** — `.build()` 를 붙이면 컴파일되지 않는다 (1.x 는 `ChatOptions`)
- **STT 는 브라우저에서 한다** — 화자 구분이 공짜로 되고, `confidence` 는 오인식 탐지에 쓸모가 없다 → [발화수집-STT.md](발화수집-STT.md)
- **발화별 판단은 안정적이고 조합 탐색은 불안정하다** — LLM 에게는 하나씩 보는 분류를 시키고, 조합은 코드가 만든다. 진술대조권 B안의 근거 (8회 관찰)
