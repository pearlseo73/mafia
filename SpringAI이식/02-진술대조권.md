## 2. 입력

| | |
|---|---|
| 화자 | **지목 대상만** |
| 시점 | 아이템 사용 시각 **이전** (`now` 자체 제외) |
| `phase` | `NIGHT` 제외 (공통 로더가 이미 함) |
| 라운드 | 제한 없음 — 게임 처음부터 |
| 프롬프트에 넣는 값 | 대상 닉네임 · 번호 붙인 발화 목록 |
| 프롬프트에 **안** 넣는 값 | 사용 시각 (컷오프 기준으로만 쓴다) · 역할 · 투표 내역 |

### 🔴 대상 발화만 주는 것이 이 기능의 핵심이다

각 조건 3회 실측 (2026-07-29).

| 입력 | 결과 |
|---|---|
| 전원 발화 65건 | 3회 정답. 단 **곰돌이가 모순을 짚어주는 발화 3건 덕**이었다 |
| 해설 3건만 제거 | **3회 전부 오답.** 대상과 무관한 발화를 짝지었다 |
| **대상 발화 8건만** | **3회 전부 정답.** 입력 2,415 → 535토큰 |

맥락 54건은 노이즈로 작동하고, 해설이 그 노이즈를 덮고 있었을 뿐이다. **맥락 주입(대상 발화 직전 1~2줄)도 기각됐다** — 좋아질 것으로 봤으나 실측이 반대였다.

---

## 3. 발화 번호 — 환각 방어의 토대

```
rows  — 렌더용. (번호, 발화) 쌍
byId  — 검증·치환용. "u5" → 발화 원본
```

**둘을 같은 순회에서 만든다.** 따로 만들면 번호가 어긋나고, 그러면 ④의 검증과 ⑤의 치환이 서로 다른 발화를 가리킨다.

번호는 **시간순**이고 대상 발화만 센다 (전체 로그의 인덱스가 아니다).

---

## 4. 렌더 — 글자 단위로 맞춘다

```
 u1 [R1 토론 21:00:57] 밥하늘 씨 말도 일리가 있어요 보통 마피아가 먼저 판을 짜려고 하니까
 u2 [R1 토론 21:01:12] 저는 딸기우유 씨가 제일 수상해요 …
 u3 [R1 심판 21:04:08] 저 방학과 있습니다
u10 [R3 토론 21:10:45] …
```

| 요소 | 규칙 |
|---|---|
| 번호 | **폭 3으로 오른쪽 정렬** — `u1` 은 앞에 공백 1칸, `u10` 은 없다. Python `f"{uid:>3}"` = Java `String.format("%3s", uid)` |
| 대괄호 | `[R{round} {페이즈라벨} {t}]` |
| 화자 이름 | **넣지 않는다** — 전부 대상이라 군말이다 (541 → 525토큰) |
| 구분 | 한 발화당 한 줄, `\n` 으로 연결 |

> 🔴 **번호 정렬 공백을 빠뜨리기 쉽다.** 렌더 스냅샷과 비교하면 바로 걸린다.

### `phase` 가 없으면 이 기능이 깨진다

라면왕(모순 없는 인물) 각 조건 3회.

| 프롬프트 | `phase` 없음 | `phase` 있음 |
|---|---|---|
| 명령형 "번호 두 개를 답하시오" | `u12` 오독 3/3 | 오답 3/3 |
| 조건형 "모순이 있는 경우에만" | `u12` 오독 3/3 | **모순 없음 3/3** ✅ |

`phase` 가 없으면 투표 단계의 "저는 딸기우유 씨입니다"를 **정체 주장으로 읽고** 다른 발언과 모순이라고 답한다. **두 변경이 서로 다른 문제를 고친다** — `phase` 는 오독을, 조건형 USER 마지막 줄은 "없을 때 없다고 말하는 능력"을 담당한다. **하나만 넣으면 TC-5 가 깨진다.**

## 5. 프롬프트

### SYSTEM — 규칙 3개뿐

12개짜리 버전보다 실측 성적이 좋았다. 뺀 것과 이유:

| 뺀 규칙 | 근거 |
|---|---|
| 의견 변화 vs 과거 진술 왜곡 구분 | 안 가르쳐도 모델이 한다 |
| STT 로 깨진 발화 처리 | 안 가르쳐도 한다 — `u2` 의 "너를 생각입니다"가 깨졌는데 "제일 수상해요"를 근거로 썼다 |
| 같은 방향 짝짓기 금지 | **넣어도 지켜지지 않았다** (우호끼리 짝지은 회차가 나왔다) |
| 중복 묶음 금지 | 짝이 하나라 해당 없음 |

**규칙 2("누가 마피아인지 추측하지 않는다")는 반드시 남긴다.** 없이 돌렸을 때 모델이 답변 끝에 "초코비의 정체가 마피아일 가능성까지 추론해드릴게요"라고 **먼저 제안했다.** 절대 규칙 2 위반 직전이고, 작업을 범인 찾기로 이해했다는 신호다.

### USER — 마지막 줄은 반드시 조건형

```
모순이 있는 경우에만 서로 충돌하는 발언 번호 두 개를 답하시오.
```

명령형("번호 두 개를 답하시오")이면 **모순이 없어도 두 개를 만들어낸다.** 사실상 "반드시 찾아라"가 된다.

**"두 개"로 개수를 못 박은 결과 3회 전부 같은 짝이 나왔다.** 여러 개를 요구하면 회차마다 개수가 흔들렸다 (8회 관찰).

## 6. 출력 계약

```jsonc
// 모순을 찾았을 때
{"hasFindings": true, "ids": ["u2", "u5"], "reason": "한 문장"}

// 모순이 없을 때
{"hasFindings": false, "ids": [], "reason": ""}
```

`record` 로 받는다 (`hasFindings` · `ids` · `reason`). **`.entity()` 는 쓰지 않는다** — 형식 지시는 이미 SYSTEM `.st` 안에 있다.

## 7. 코드가 하는 검증 — 순서대로

### ① 임계값 — 호출 전에 막는다

```
대상 발화가 3건 미만  또는  총 글자수 40자 미만  →  호출하지 않고 INSUFFICIENT 반환
```

**호출하지 않으면 억지 모순이 만들어질 일도 없다.** 프롬프트로 "없으면 없다고 해라" 부탁하는 것과 다르다 — **부탁은 새고, 호출을 안 하는 것은 안 샌다.** (TC-4 소금빵 2건 28자)

`3` · `40` 은 **잠정값**이다. R1 토론 중에 쓰면 6명 중 3명이 미달이다 → [결정필요사항 T8](참고/결정필요사항.md).

### ② 없는 번호 버림

```
byId 에 없는 번호는 제거한다
```

**프롬프트 품질과 무관하게 보장되는 환각 방어다.** 프롬프트를 어떻게 고쳐도 `byId` 밖의 번호는 여기서 죽는다.

### ③ 짝이 2개 미만이면 결과가 아니다

```
검증 후 남은 ids 가 2개 미만이면 hasFindings = false
```

모순은 두 발언 사이에서만 성립한다.

### ④ 파싱 실패

예외를 던지지 않고 "실패"로 돌려 폴백 판단에 쓴다.

## 8. 응답 조립 — 번호를 원문으로 치환

**이 기능에서 발화 원문이 등장하는 유일한 지점이다.** 모델은 원문을 쓰지 않았으므로 **없는 발언이 만들어질 수 없고 인용이 잘릴 일도 없다.**

```
u5 → byId["u5"] → [R2 21:06:20] 마음이 바뀐 겁니다 …
```

### 🔴 실서비스 주의

**`byId` 와 발화 번호는 서버에만 둔다. 프론트로는 치환된 원문만 내려보낸다** → [AI-API명세 §2-5](참고/AI-API명세.md).

## 11. 미결 — 이식과 함께 결정할 것

- **어느 짝이 나올지 회차마다 다르다.** 셋 다 정답이지만 재현되지 않는다. `u7`×`u8`(25초 간격 정면 자기모순)이 `u2`×`u5`("마음이 바뀐 겁니다"라는 해명이 붙어 반박 가능)보다 강하다 → 고르고 싶으면 판정 B안(LLM 분류 → 코드 조합)이 필요하다
- **`u5`×`u6` 을 못 잡는다** — "처음부터 믿었습니다" 하고 2분 뒤 그에게 투표. 유효한 후보인데 짝을 하나만 받아서 안 나온다
- **`u5` 는 STT 병합 발화다** — 해명과 모순이 한 발화라 잡으면 정답·오답이 동시에 성립한다. 프롬프트로 풀 문제가 아니다
- **생존 검사(TC-7) 미구현** — 실서비스에서는 `TARGET_NOT_ALIVE` 로 먼저 막혀야 한다
- **투표 내역(TC-3) 미구현** — `phase` 와 같은 "서버가 아는 사실" 계열이라 함께 검토할 값어치가 있다
