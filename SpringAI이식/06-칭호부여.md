# 06. 🏆 칭호 부여 (Task 22)

> 노트북: `# 5. 칭호부여` 셀 5개 · 설계 [AI기능-구현설계 §5](참고/AI기능-구현설계.md)
> 프롬프트: [title-award-system.st](prompts/title-award-system.st) · [title-award-user.st](prompts/title-award-user.st)
> 렌더 기준값: [렌더스냅샷/칭호-user.txt](렌더스냅샷/칭호-user.txt)

**역할을 LLM 에 주는 유일한 기능이다.** 게임 종료 = 역할 공개 시점이므로 절대 규칙 2 의 예외다.

**게임당 1회 호출이라 지연이 문제되지 않는다.** 입력이 가장 크다 (4,077토큰).

---

## 1. 입력

### 서버가 조회하는 것 5개

1. 참가자 닉네임 목록
2. **플레이어별 역할** (시민 / 마피아)
3. 사망 기록 — 누가 · 몇 라운드 · 원인 · **그때의 `phase`**
4. 최종 승리 진영과 생존자
5. 낮 공개 발화 전체

### LLM 에 넘기는 것 4개

1. 최종 승리 진영
2. 플레이어별 역할
3. 플레이어별 **사망 라운드와 원인** (생존자는 생존 표시)
4. **낮 공개 대화 전체** (컷오프 없음)

**승패는 넘기는 값에 없다.** `승리 진영 + 역할` 의 결과라 새 정보가 아니고, **코드가 계산한다** — 모델이 매번 역산하게 두면 틀릴 여지만 생긴다.

**조회 3 의 `phase` 도 넘기지 않는다** — 사망 원인 3종을 가르는 데만 쓴다 (§2).

### 🔴 낮 대화로 알 수 있는 것은 넘기지 않는다

발화량 · 득표 · 투표 내역 · 이름 언급 횟수를 **빼면 모델이 그 숫자를 틀릴 일도 없어진다.** LLM 이 대본을 보고 판단한다.

**같은 사실을 두 번 주면 모델이 어느 쪽을 근거로 삼았는지 알 수 없다.** AI 심판과 정반대 방침이다 — 심판은 통계를 주고 칭호는 안 준다.

USER 프롬프트에 `{votes}` 자리가 있는데, 서버 전달값에서 투표 내역을 뺐으므로 이 문구가 들어간다.

```
(서버 투표 집계는 제공하지 않는다. 낮 대화의 투표 구간 발언을 참고하라.)
```

낮 대화의 `DAY_VOTE` 구간에 "저는 초코비 씨입니다" 같은 투표 발언이 남아 있어 모델이 그것으로 판단한다. **서버 집계를 다시 주기로 하면 이 상수만 바꾸면 된다.**

### 🔴 밤 대화는 넣지 않고 경로도 선언하지 않는다

**2026-07-31 확정.** 전에는 opt-in 이었다. 밤 구간에서 쓰는 것은 **서버 이벤트(사망)뿐**이고, 금지 대상은 대화 원문이다.

근거 — 픽스처의 밤 로그는 **9건 197자**뿐이라 얻을 것이 적고, 경로를 만들어두면 낮 기능이 실수로 닿을 수 있다 → [AI기능-구현설계 §2-3](참고/AI기능-구현설계.md).

## 2. 사망 원인 3종은 `phase` 로 가른다

**AI 심판 처형과 최후변론 처형이 이벤트 로그에서 둘 다 `cause=EXECUTION` 이다.** 구분되는 것은 그때의 `phase` 뿐이다.

| 조건 | 라벨 |
|---|---|
| `cause=NIGHT_KILL` | 마피아에게 살해당함 |
| `cause=EXECUTION` **AND** `phase=AI_JUDGMENT` | AI 심판 지목으로 처형됨 |
| `cause=EXECUTION` (그 외) | 최후변론 투표로 처형됨 |

**시나리오1 에는 AI 심판 사망이 없다** — 초코비가 방어권으로 막았다. 이 분기는 다른 픽스처로 확인해야 한다.

## 3. 렌더

### 플레이어 정보 — 1명당 4줄

```
■ 라면왕
  역할: 시민
  결과: 승리
  생존: 끝까지 생존

■ 밤하늘
  역할: 시민
  결과: 승리
  생존: R2에 사망 — 마피아에게 살해당함
```

- 들여쓰기 **공백 2칸**
- `결과` = `역할 == 승리진영` 이면 승리, 아니면 패배 (코드가 계산)
- `생존` = `끝까지 생존` 또는 `R{n}에 사망 — {사망라벨}`
- 블록 사이 **빈 줄 하나**

### 낮 대화 — AI 심판과 같은 형식

```
[R1 시작 21:00:04] 라면왕: 이 시작했네요
```

`[R{round} {페이즈라벨} {t}] {speaker}: {text}` — **전체 79건이 다 들어간다** (컷오프 없음).

> 조간신문에서 이 형식이 주체를 뒤집었다. 프롬프트 문안을 그대로 쓰기로 했으므로 이대로 두고, **시상평에 주체가 뒤집히는지 눈으로 확인한다.**

## 4. 프롬프트 — SYSTEM 1,678자 (본문 1,356 + 출력 계약 322)

### 🔴 출력 계약은 따로 붙인 것이다

**받은 문안(`SYSTEM_BASE_TT`)에는 출력 형식 지시가 없다.** 그대로 보내면 JSON 이 아니라 줄글이 온다. "출력 형식" 절을 뒤에 붙여서 `SYSTEM_TT` 를 만들었다.

`.st` 파일 [title-award-system.st](prompts/title-award-system.st) 는 **둘이 합쳐진 상태**다. 나중에 받은 문안이 갱신되면 뒤쪽 "출력 형식" 절만 유지하고 앞을 갈아끼운다.

### 역할 — 시상식 사회자

칭호 선정 기준 4종: 추리와 투표 · 회의 참여 방식 · 역할과 경기 결과 · 아이템과 생존.

### 작성 규칙 중 계약인 것

```
- 모든 플레이어에게 칭호를 정확히 하나씩
- 입력에 있는 모든 플레이어를 빠짐없이
- 서로 다른 플레이어에게 같은 칭호를 부여하지 않는다
- 서버가 제공한 역할·승패·투표·생존·아이템 기록을 변경하지 않는다
- 입력에 없는 사건·발언·횟수를 만들지 않는다
- 밤 대화나 밤에 있었을 법한 발언을 추측하지 않는다
- 단순히 역할만 보고 칭호를 정하지 않는다
```

`quote` = 해당 플레이어에게 **직접 건네는 한 문장** 시상평.
`reason` = 칭호 선정 근거. 실제로 확인되는 내용을 짧고 구체적으로.

### 칭호 예시 16종은 USER 에 있다

`역대급 억울함` `완벽한 추리` `소름 돋는 거짓말` `웅변가` `침묵의 암살자` `인간 확성기` `의심 제조기` `국민 변호사` `여론 장악자` `갈대왕` `뚝심의 추리왕` `무고한 희생양` `자백 직전상` `촉이 왔다상` `완전범죄` `최고의 팀킬상`

**그대로 써도 되고 새로 만들어도 된다**고 지시한다 (§8 의 A/B 결정과 얽힌다).

## 5. 출력 계약

```jsonc
{"titles": [{"nickname": "라면왕", "title": "뚝심의 추리왕",
             "quote": "첫 의심을 끝까지 놓지 않은 집념이 결국 마을을 구했습니다.",
             "reason": "초코비를 꾸준히 의심하고 마지막 라운드에 실제로 투표해 시민 승리에 기여했다."}]}
```

- `titles` 는 **참가자 수와 같은 길이**

**검증용이다.** 실제 API 응답에는 `nickname` · `title` · `quote` 만 넣는다 → [AI-API명세 §1-3](참고/AI-API명세.md).

## 6. 검증 — 계약 위반만 센다

| 검사 | 실패 조건 |
|---|---|
| 구조 | JSON 객체가 아니다 / `titles` 가 배열이 아니다 / 배열 안에 객체가 아닌 항목 |
| **누락** | 참가자가 결과에 없다 |
| **중복 배정** | 같은 참가자가 두 번 나왔다 |
| **없는 닉네임** | 입력에 없는 닉네임이 나왔다 |
| **칭호 중복** | 서로 다른 참가자가 같은 칭호를 받았다 |
| 빈 항목 | `nickname`·`title`·`quote`·`reason` 중 빈 것 |

**재미와 톤, 사실 충돌은 눈으로 본다.** 어서션 러너를 만들지 않는다 (CLAUDE.md) — 기대답안은 참조 샘플이다.

### 실측된 파싱 실패 원인은 하나였다

**`reason` 안에서 발언을 큰따옴표로 감싸 JSON 문자열이 끊겼다.** 반복되면 출력 계약에 "인용은 작은따옴표만" 한 줄을 넣는다.

## 7. 전원을 한 번의 호출로 받는다

**칭호 중복 금지가 계약이라 서로를 봐야 한다.**

- 한 명씩 6번 호출하면 모델이 **다른 사람에게 무엇을 줬는지 모른다**
- 코드로 사후 제거하면 **누구의 칭호를 버릴지 정해야 하는데 그 기준이 없다**

**이것은 CLAUDE.md 의 "여러 개를 요구하면 흔들린다"와 정면으로 부딪히는 지점이다.** 6명 동시 요구라 흔들림·중복·환각이 다 여기서 나온다 → §8.

## 8. ✅ B 안으로 확정 (2026-07-31)

| | 안 | |
|---|---|---|
| ~~A~~ | ~~LLM 이 칭호명 + 대사 창작~~ (현재 노트북) | **기각.** 6개 동시 요구라 흔들림·중복·환각이 다 여기서 나온다 |
| **B** | **16종을 고정 세트로 두고 서버가 지표로 매칭, LLM 은 대사만** | ✅ **채택** |

**근거** — 16종 중 10종이 이미 숫자로 정의돼 있다("발화량 1위", "시민인데 최다 지목"). 진술대조에서 배운 **"조합은 코드가 만들고 LLM 은 문장만"** 을 그대로 적용하는 자리다. **중복·환각이 구조적으로 불가능해지고 폴백이 곧 본로직이 된다.**

지표가 애매한 사람에게만 A 를 쓰는 혼합은 남겨둔다 (§8-3).

### 8-1. B 로 바뀌는 것

| | A (노트북 현재) | **B (확정)** |
|---|---|---|
| 칭호명 | LLM 이 창작 | **서버가 지표로 매칭** |
| `quote` (시상평) | LLM | LLM |
| `reason` (근거) | LLM | **서버 지표 + LLM 문장** |
| 중복 방지 | 프롬프트 규칙 + 사후 검증 | **구조적으로 불가능** (1칭호 1인 배정) |
| 호출 방식 | 전원 한 번에 (중복 금지 때문) | **한 번에 유지** — 대사 톤이 서로 겹치지 않게 |
| 폴백 | 결산 화면 지연 | **칭호는 이미 정해져 있다.** 대사만 기본 문구로 |

**폴백이 본로직과 같아지는 것이 B 의 가장 큰 이점이다.** LLM 이 죽어도 칭호는 나간다 — 재미만 줄어든다. 조간신문의 2단 조립과 같은 성격이다.

**프롬프트도 바꿔야 한다.** 현재 [title-award-system.st](prompts/title-award-system.st) 는 "가장 잘 어울리는 칭호를 정확히 하나씩 부여하라"이고, B 에서는 **"이미 정해진 칭호에 맞는 시상평을 써라"** 가 된다. 출력 계약에서 `title` 이 입력으로 옮겨간다.

```jsonc
// B 의 출력 계약 (안) — title 은 서버가 정했으므로 되받지 않는다
{"quotes": [{"nickname": "라면왕", "quote": "첫 의심을 끝까지 놓지 않은 집념이 …"}]}
```

`title` 을 되받지 않으면 **칭호 환각이 원천적으로 불가능하다.** 진술대조가 원문을 되받지 않는 것과 같은 방어다.

### 8-3. 🔴 B 에서도 남는 문제 — 곰돌이와 라면왕

적중 3/3 이 같고 발화량도 21건 vs 20건이라 **지표로 구분이 안 된다.** B 는 중복을 막아주지만 **"둘 중 누구에게 어느 칭호를 줄지"** 는 여전히 정해야 한다.

가능한 처리 세 가지.

| 안 | 내용 |
|---|---|
| 우선순위 규칙 | 지표에 순위를 매겨 동점이면 **다른 지표로 타이브레이크**한다. 라면왕은 시민 중 받은 표 최다(4표)라 `무고한 희생양` 으로 갈라진다 |
| 남은 칭호에서 배정 | 강한 칭호부터 배정하고 남은 사람에게 남은 칭호를 준다 (탐욕 배정) |
| **애매한 사람만 LLM** | 지표로 확정되는 사람은 서버가 정하고, 남은 사람만 LLM 에게 후보 몇 개를 주고 고르게 한다 — A/B 혼합 |

**여기가 TC-25·TC-26 이 실제로 깨지는 자리다.** B 로 가도 이 배정 규칙을 안 정하면 같은 문제가 남는다.
